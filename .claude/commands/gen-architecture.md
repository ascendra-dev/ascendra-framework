# Generate Architecture Document

You are generating the Architecture Document for an Ascendra client project. This is Gate 5 — the mandatory technical blueprint read before any implementation begins. No development begins until this document is approved and Locked by the Product Owner.

The architecture document defines: project repository naming, folder structure, tech stack, every backend module, every database table, every API endpoint, the security model, seed data, and all environment variables. `/implement-story` implements exactly what is defined here — nothing more, nothing less.

Generate each Tier 1 (cross-cutting baseline) file as follows, using `technical-standard.template.md`'s shape:

**`api-standards.md`** — apply `reference/api-contract/contract.md` (`FW-042`) as the fixed base:
response shape for single objects and lists, error shape, HTTP method semantics (including the
state-transition `POST`-with-action-segment pattern), pagination query params/response fields, and
header conventions (`X-Request-Id`, `Idempotency-Key`, `If-Match`/`ETag`) are pinned there and never
re-derived — cite the file, do not restate its rules. This file adds only what genuinely varies per
project:
- Base URL path and versioning convention (e.g. `/api/v1/`)
- The concrete name of this stack's typed business-rule exception (`code` is populated only for
  it, per contract Rule 2) — e.g. `BusinessRuleViolationException` for NestJS
- Resource and path naming convention (case, plural vs singular)
- Which specific endpoints enforce `Idempotency-Key` server-side (contract Rule 7 — enforcement is
  opt-in per endpoint, decided per project)
- **If — and only if — `database-standards.md`'s Section 4.2 table decisions use optimistic
  locking on any table (`FW-045`/`FW-046`):** the concrete name of this stack's typed stale-version
  exception (`code: 'STALE_VERSION'` populated only for it, per contract Rule 8) — e.g.
  `StaleVersionException` for NestJS — and confirmation that it is a distinct exception type from
  the business-rule exception above, not a second status code on the same class. State plainly "Not
  applicable — no table uses optimistic locking" if none do, rather than omitting the bullet
  silently (the omission itself needs to be a recorded decision, not an accident).
- CORS / cross-origin policy: which origins are allowed and how configured (the env var name, e.g. `ALLOWED_ORIGINS`) — required whenever the frontend and backend are separate repos or origins, which is this framework's standard multi-repo topology; state explicitly where in the bootstrap code this gets wired in, not just that the env var exists
- Any framework-specific conventions for this stack (e.g. NestJS controller structure, decorator pattern)

**`database-standards.md`** — derive from the confirmed database and ORM:
- Table naming convention (case, plural or singular)
- Column naming convention (case)
- Primary key: type and generation method
- Standard columns required on every master table — state the actual set explicitly, never just "standard columns": `id`, tenant/org identifier (if multi-tenant), `version` (`FW-045` — optimistic locking is the default expectation for any Master table more than one actor can concurrently mutate, which describes nearly every Master table in a multi-user system; omit only with a stated reason, e.g. a genuinely single-writer table, never silently by default — same standard as the actor-column rule immediately below), the `created_at`/`updated_at`/`deleted_at` timestamp trio, **and their actor counterparts `created_by`/`updated_by`/`deleted_by`** — a row's full write history (when, and by whom, for creation, every update, and every deletion) is the default expectation for an auditable system, not just when it was created. Omit an actor column only with a stated reason (e.g. a table with no application-level actor concept), never by default.
- **Shape of the actor columns (`FW-037`/`FW-038`):** determined by Step 4's confirmed Actor Identity Shape, not assumed:
  - **Single actor identity space:** `uuid`, foreign-keyed to that one actor table (e.g. `created_by uuid references users.id`) — gets referential integrity and joinability for free, and is the simpler choice when it's correct.
  - **Multiple actor identity spaces:** a self-contained actor-label column instead — `varchar`, no foreign key, no companion type-discriminator column (a bare untyped id would be unresolvable across more than one target table, and a type column was deliberately rejected on cost/consistency grounds — see `FW-037` for the full reasoning). Populated by the calling code at write time: an authenticated session resolves it from the session's own name claim; a non-authenticated actor (e.g. a tokenized-link customer) resolves it from whatever record identifies them for that action; a background/scheduled job or webhook uses a fixed, centralized literal (e.g. `'System (...)'`) — never invented ad hoc per call site.
  - State whichever shape was confirmed, and why, directly in the generated file — do not leave the choice implicit.
- Standard columns required on every detail table — same principle, scoped to what applies: if detail rows are immutable once created (a common, valid detail-table pattern), `updated_at`/`updated_by`/`deleted_at`/`deleted_by` do not apply and should be omitted with that stated reason; `created_at`/`created_by` still apply even to immutable rows.

If the confirmed shape is the actor-label variant, the threaded value is already the resolved label itself — no id/foreign-key concern applies. Either way, which of the three columns gets written is decided by the operation being performed (an insert sets `created_by`, an update sets `updated_by`, a soft-delete sets `deleted_by`), never by a type/flag parameter passed alongside the actor value.
