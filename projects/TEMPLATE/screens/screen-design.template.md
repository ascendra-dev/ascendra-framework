# Screen Design Template

> **[AI Guide — Document Level]**
> Screen Design is generated by `/gen-screen-design` after Epic Approval and before `/gen-architecture` — it covers the three parts of screen structure (Portals, Navigation Map, Screen Inventory) that only ever depended on the BRD, never on a confirmed tech stack. It reaches its approval gate (`Approved`) via `/review-screen-design`; architecture cannot begin until this document is `Approved`.
>
> Every screen in Section 3 is pattern-matched against `ascendra-ui`'s real component catalog (`ascendra-ui/docs/ui-reference.md`, `ascendra-ui/docs/showcase-reference.md`) — a Surface (Page/Dialog/Sheet/Drawer) and UI Pattern (Form/Dashboard/Report/Table-List/Detail), each cited to a specific named catalog entry or, for Report/Table-List (which have no Part 2 composite example), a primitive composition. A citation to a real, inspectable example is mandatory — an invented shape with no catalog match is a defect, not a judgment call.
>
> **When used by `/gen-screen-design`:** writes this document in full — Sections 1–4 — from the approved BRD and domain knowledge, then presents it to the PO for confirmation before saving.
> **When used by `/review-screen-design`:** read in full for the structured PO review that gates this document to `Approved`.
> **When used by `/gen-architecture`:** Sections 1–3 (Portals, Navigation Map, Screen Inventory) are carried into architecture Section 3.1.3.1–3.1.3.3 as-is, not re-derived. Section 4 (Data Requirements) feeds Section 4 (Data Model) and Section 5 (API Contracts) of the architecture document.
> **When used by `/gen-ui-mocks`:** read for Portals/Navigation Map/Screen Inventory/Surface/UI Pattern/Matched Reference when generating the first (base-mode) pass of the HTML mocks, before architecture exists.
> **When used by `/implement-story`:** read for the specific screen(s) a Web story touches — Surface, UI Pattern, and Matched Reference decide what gets built, so implementation matches the mock the PO already approved instead of guessing independently.
>
> **What this document is not:**
> - Not the full Screen & Navigation Map. Action Gating and Cross-Cutting UI Rules (architecture's 3.1.3.4–3.1.3.5) are not here — both need Section 6's security model, which doesn't exist yet at this point in the lifecycle.
> - Not a visual mock. This document is the structured data `/gen-ui-mocks` reads to build the actual HTML — the mock itself is not part of this file.
> - Not optional. Unlike Domain Discovery, there is no "well-known enough to skip" case — screens are specific to this project's BRD, every time.
>
> **File location:** `projects/{PROJECT_CODE}/screens/screen-design.md`
> e.g. `projects/ASCENDRA-PAY-001/screens/screen-design.md`

## Part 1 — Template

### 1. Portals

> **[AI Guide]** One row per genuinely distinct navigation shell, derived from BRD Section 2 (Personas) and Section 3 (User Roles) — not one row per persona. Two personas share a portal if they log into the same app and their navigation differs only by which items are visible. If BRD Section 6.3 (Delegated Access) is populated, name the delegated session as entering an existing portal, not as its own row.

### 3. Screen Inventory

> **[AI Guide]** One row per screen. Derive from BRD Section 4 (User Journeys) and Section 5 (Functional Requirements) — every journey step or requirement with a "persona can see/do X" shape gets a row. A screen missing from this table is a gap to close now, not something to leave for `/gen-ui-mocks` or `/implement-story` to invent.
>
> **Surface and UI Pattern are mandatory, cited fields — never a bare category label.** For every row:
> - **Surface** (Page / Dialog / Sheet / Drawer): decided from the source journey/FR's language. "Without leaving the page" / "quickly" / "inline" signals an overlay, not a route change. Page surfaces use `ascendra-ui`'s `Header` breadcrumbs for back-navigation (there is no dedicated back-button primitive); Dialog/Sheet/Drawer use their documented `showCloseButton` (×) instead.
> - **UI Pattern** (Form / Dashboard / Report / Table-List / Detail): matched against `ascendra-ui/docs/ui-reference.md` Part 2's own classification columns (Forms: `Domain | Complexity | Layout`; Dialogs/Sheets/Drawers: `Type | Components`, Sheets/Drawers also `Domain`; Dashboards: `Domain | Chart types | KPIs`). Report and Table-List have no Part 2 composite example — cite a primitive composition instead (e.g. "Report Header + Report Document + Report Content", or "Data Table + Empty State + Page Bar").
> - **Matched Reference** names the specific catalog entry or primitive set matched — never left blank, never a generic restatement of the UI Pattern column.
> - **Tabs**: only propose when the source journey/FR describes 2+ independent sub-views reachable from one entry point with no route change — layered onto whatever Surface/Pattern was already chosen, not a default.
> - **Empty State**: note as a secondary state (in the Notes column) on List/Table-List/Dashboard screens plausibly starting with zero records (new tenant, first-run) — this is a state of the screen, not a screen type of its own.
> - **Command Palette** and **Toast** are never matched per screen — Command Palette is cross-cutting (belongs in architecture's future 3.1.3.5 if the BRD signals a power-user/admin role); Toast is ephemeral and cannot be meaningfully shown in a static mock — do not attempt either here.
>
> **Correct:** `Surface: Dialog (Input type, showCloseButton: false) — Matched Reference: "Invite Member" (Dialog, Input, Select, Field, Button) — because journey step 3 says "Finance Manager can quickly add a payment method without leaving the dashboard."`
> **Incorrect:** `Surface: Modal — Matched Reference: standard form dialog` — a generic label with no real catalog citation is not a valid match.
