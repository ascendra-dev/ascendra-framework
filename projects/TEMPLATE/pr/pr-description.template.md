# PR Description Template

> **[AI Guide — Document Level]**
> The PR description is filled in by the Engineering Agent when creating a GitHub pull request. It is the primary communication artifact between the Engineering Agent and the Product Owner (reviewer). A reviewer who reads only the description — without opening a single file — must understand what changed, why, and how to verify it.
>
> **One story = one PR.** A PR that covers more than one story is too large. If the Summary cannot be written in two sentences, the PR is too large — split it before creating the PR.
>
> **The PR title must follow Conventional Commits format before the description is started:**
> `type(scope): subject` — e.g. `feat(invoice): add reference number generation`
> Valid types: `feat`, `fix`, `refactor`, `test`, `chore`, `perf`
> The Type of Change checkbox in Section 2 must match the type in the PR title exactly.
>
> **Ticket link format:** use `Closes` to auto-close the story ticket on merge. Use `Refs` if the ticket spans multiple PRs and should remain open after this PR merges. The project key prefix varies by project — replace `ASC` with the project's ticket prefix (e.g. `ASCE`, `HBV`).
>
> **Screenshots:** include for any change that affects a visible UI element — layout, colour, text, state. Delete the Screenshots section entirely for backend-only PRs. Do not include screenshots for routes that return JSON.
>
> **File location:** `projects/{PROJECT_CODE}/pr/US-{epic}-{seq}-pr-description.md` — one file per story, generated by `/gen-pr-description`.
> e.g. `projects/ASCENDRA-PAY-001/pr/US-04-001-pr-description.md`

## Part 1 — Template

---

**PR Title:** `type(scope): subject` — e.g. `feat(payer): register payer via manual form`

> **[AI Guide — PR Title]** The PR title is set in GitHub, not in the body. Confirm the title is in Conventional Commits format before filling in the body. The `type` must match the checkbox ticked in Section 2. The `scope` is the NestJS module or Next.js feature area affected (e.g. `invoice`, `auth`, `payer`, `client`). The `subject` is a short imperative phrase: "add", "fix", "remove" — not "added", "fixes", "removing".

---

### 1. Summary

> **[AI Guide]** One or two sentences. Answer: what changed, and why was this change needed? Written for someone who has not read the story — they should understand the purpose of this PR without looking at the code.
>
> Follow the Summary with the ticket link on its own line. Do not bury the ticket link in prose.
>
> **Correct:** "Adds the invoice reference number generation service, assigning a unique INV-YYYY-NNNNNN reference to each new invoice at creation time. Required by REQ-008 — the reference number is the primary identifier for invoice tracking and customer communication."
>
> **Incorrect:** "This PR implements the story" (no context) or a paragraph describing every file touched (that belongs in Section 3).

[1–2 sentences: what changed and why]

Closes [PROJECT-KEY]-[id]

---

### 2. Type of Change

> **[AI Guide]** Tick exactly one. The type must match the `type` prefix in the PR title. If the change genuinely crosses two types (e.g. a bug fix that also adds a test), it is two PRs — one `fix`, one `test`. The only exception: `test` additions that directly accompany a `feat` may be included in the same PR and the type is `feat`.
>
> - `feat` — new capability that did not exist before; a user or system can now do something new
> - `fix` — corrects incorrect behaviour; does not add new capability
> - `refactor` — restructures existing code with no behaviour change; all tests pass before and after
> - `test` — adds or updates tests only; no production code changes
> - `chore` — tooling, dependency updates, configuration, CI/CD — nothing a user would notice
> - `perf` — improves performance of existing behaviour with no behaviour change

- [ ] `feat` — new feature
- [ ] `fix` — bug fix
- [ ] `refactor` — no behaviour change
- [ ] `test` — tests only
- [ ] `chore` — tooling, deps, config
- [ ] `perf` — performance improvement

---

### 3. What Changed

> **[AI Guide]** Factual bullet list of the specific changes in this PR. Cover every meaningful file or behaviour change. This is a changelog entry, not a code walkthrough — do not explain how the code works, only what changed.
>
> **Structure each bullet as:** `[file or module] — [what changed]`
> e.g. "InvoiceService — added `generateReferenceNumber()` method using a PostgreSQL global sequence"
>
> **Target 3–7 bullets.** Fewer than 3 usually means the description is incomplete. More than 7 usually means the PR is too large.
>
> **Do not include:** test files in the same bullet as production files (list them separately), implementation detail that would only make sense to the author, or bullets that duplicate what the Summary already said.

- [Module or file] — [what changed]
- [Module or file] — [what changed]

---

### 4. How to Test

> **[AI Guide]** Numbered steps a reviewer can follow to verify this PR works, starting from a clean state. The reviewer must be able to follow these steps without asking a follow-up question.
>
> **Always include:**
> - Starting state — what must exist before step 1 (e.g. "a seeded database with at least one client record")
> - The happy path — the primary flow that proves the story's acceptance criteria are met
> - At least one edge case or validation check — a negative path that proves the guard rails work
>
> **Do not write:** "run the tests" as a step — CI does that. Do not write steps so vague that the reviewer must make judgment calls ("verify it works correctly"). Write what the reviewer should see, not what they should think.
>
> **API-only PRs:** include the exact `curl` command or Postman request, including headers. Do not assume the reviewer knows the request shape.

1. [Starting state — what must exist]
2. [Action]
3. [Expected result]

---

### 5. Screenshots

> **[AI Guide]** Required for any change that affects a visible UI element. Include a before/after pair if the PR modifies existing UI. A single screenshot if it adds new UI.
>
> **Delete this section entirely for backend-only PRs.** Do not leave it in with "N/A" — a blank section wastes the reviewer's attention.

[Screenshot]

---

### 6. Pre-Merge Checklist

> **[AI Guide]** The Engineering Agent completes this checklist before submitting the PR for review. The reviewer verifies it — a PR submitted with unchecked boxes will be returned without review.
>
> Every item below applies to every PR. If an item is not applicable (e.g. no migration in this PR), tick it and add "— N/A" after the label rather than leaving it unchecked. An unchecked box signals a gap, not an inapplicable item.

- [ ] PR title follows Conventional Commits format — `type(scope): subject`
- [ ] Type of Change has exactly one box ticked and it matches the PR title type
- [ ] All CI checks pass — no failing tests, no lint errors, no build errors
- [ ] No `.env` files, secrets, or credentials committed
- [ ] New database migrations include the `set_updated_at` trigger for any table with an `updated_at` column
- [ ] `orgId` is sourced from the JWT payload — not from the request body, URL parameter, or query string (backend PRs)
- [ ] React Query cache is invalidated in the relevant mutation hook for any endpoint that mutates data (frontend PRs)
- [ ] Screenshots are included for any visible UI change — section deleted if backend-only

---

### 7. Density & Judgment Findings

> **[AI Guide]** Written only by `/judgment-check` — never filled at `/gen-pr-description` time, and left out of the document entirely until that command has actually run once. This section holds one run's worth of findings against `practitioner-guide/08-development.md`'s own tests (the diff-fidelity discipline, and the Pre-Merge Checklist's two stack-specific items — `orgId` from the JWT and React Query cache invalidation — that FW-029/FW-030 flag as hardcoded rather than conditioned) — questions raised for the Product Owner to weigh, never verdicts. It is replaced wholesale by each new run, never appended to — see Section 8 for the durable record of how each finding was actually resolved. If `/judgment-check` has not yet run against this PR description, this section does not appear at all; do not pre-create it empty.

### 8. Density & Judgment Resolution

> **[AI Guide]** Written only by `/judgment-check`, appended to on every run, never overwritten — the same append-only discipline as Document Control. Each row records one finding from Section 7's history and the Product Owner's actual response to it (Confirmed as-is / Revised / Acknowledged tradeoff), dated. A later run's finding covering the same spot in the document gets its own new row, never an edit to an earlier one. If `/judgment-check` has not yet run against this PR description, this section does not appear at all; do not pre-create it empty.

> **[AI Guide — numbering note]** Sections 7 and 8 are reserved for `/judgment-check` as shown here, immediately after Section 6 (Pre-Merge Checklist). There is no `/review-pr-description` command and no separate review-record file these numbers could collide with.

## Part 2 — Verification

> **[AI Guide — Verification]** Run every check below before submitting the PR. A PR that fails any check will be returned by the reviewer. The Pre-Merge Checklist in Section 6 is what the reviewer checks; this Verification is what the Engineering Agent checks before the reviewer sees the PR.

- [ ] PR title is set in GitHub in Conventional Commits format before the description body is written
- [ ] Summary is two sentences or fewer — if not, the PR is too large and must be split
- [ ] Ticket link is present using `Closes` or `Refs` — not embedded in prose
- [ ] Exactly one Type of Change checkbox is ticked and it matches the PR title type
- [ ] What Changed has 3–7 bullets — each names a specific file or module, not a vague description
- [ ] How to Test covers the happy path and at least one edge case with numbered steps
- [ ] How to Test includes a starting state — reviewer knows what must exist before step 1
- [ ] API-only PRs include the exact request (curl or equivalent) in How to Test
- [ ] Screenshots section is present for UI changes and deleted for backend-only PRs
- [ ] All Pre-Merge Checklist boxes are ticked (with "— N/A" where not applicable)
