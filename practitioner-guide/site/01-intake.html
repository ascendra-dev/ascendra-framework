Stage 1

Intake

Everything downstream traces back to one file: brief.md. Get intake thin or wrong and the damage shows up three phases later — a BRD missing a constraint nobody wrote down, an architecture decision made without knowing a regulation applied.

Two commands: /init-project creates the project; /run-intake fills brief.md section by section. Read Orientation first if you haven't.

Decision heuristic

Project boundary — one product, one project

/init-project's built-in test: a web app and its API are one project (technical components); separate portals for different user groups are separate projects. Three edge cases the one-line rule doesn't spell out on its own:

  • Teacher portal + parent portal, same school system. Two projects. Different user groups solving different problems, even sharing one backend.
  • Admin dashboard bolted onto an existing product, for the same users. Not a new project — new scope inside the existing one. Belongs in the existing project's BRD.
  • Admin/ops console for a different internal team. A separate project — very likely an Extension, since it can't be understood without the parent's domain knowledge, but it still gets its own brief.
Would this capability have its own go-live date, its own primary user group, and its own BRD sign-off, even if the "host" project never shipped it? If yes, separate project.The generalizing test

Project code format, and when to add EXT

Baseline: CLIENT-DOMAIN-NNN. The optional fourth segment (CLIENT-DOMAIN-EXT-NNN) is cosmetic — never read by any command. The real extension relationship is always the brief's Project Type/Extends/Extension Adds fields.

CodeReading
HARBORVIEW-INV-001Harborview, invoice domain, first iteration. Standalone.
ASCENDRA-PAY-CORE-001Ascendra's own payment product, core layer — base of an extension chain.
ASCENDRA-PAY-PKN-001Pakistan market layer on top of the Core project. The brief's Extends: field is the real dependency.

Not cosmetic — it changes what gets loaded into context for nearly every generating command downstream.

Decision heuristic

Interactive vs. hand-filled — sizing the session

Small internal project

You're effectively both PO and client. Hand-filling is fine and usually faster — no vague client answer for a follow-up to catch.

Medium client project

A real external client, a discovery call happened or will. Run /run-intake interactively — its follow-up prompts catch vague client answers before they're written down as specific.

Large or complex project

Regulated domain, extension chain, multiple stakeholders. Always interactive — the mandatory Verification checklist is the only mechanism forcing checks like "does every regulation cite the specific statute."

If you do hand-fill, still run the Part 2 Verification checklist in brief.template.md against your own draft — nothing else will.

Reference

Resuming, revising, amending

Intake mode (Draft)

The normal first pass. Sections 1→9 in order; anything already ✅ from an interrupted session is skipped, with an offer to review it first.

Revision mode (Brief complete)

Intake done but not yet approved. Name a section, re-runs the draft/approve loop just for it.

Amendment mode (Approved)

Any change is a tracked amendment — a one-line summary appended to a Document History table with an incremented minor version. Content Status stays Approved throughout.

Density guidance

Section by section: how much is enough

1. Problem Statement

Two to four sentences: what's happening now that shouldn't be, what it costs, what would be true if solved — from the client's perspective, never the solution. A bad Problem Statement is either too thin ("the client needs better invoicing") or already the solution ("we are building an automated reminder system").

What breaks downstream: too thin, and BRD discovery re-derives context a discovery call already surfaced. Written as a solution, and it quietly biases requirement discovery toward one implementation before alternatives get explored.

2. Client Context

Enough that someone joining mid-project understands the client without follow-up questions: who they are, scale, current process, anything that changes a design decision. Deliberately omits company history and mission statements.

What breaks downstream: too thin (no transaction volume, no team size), and neither domain knowledge nor architecture has a basis for scoping decisions. Padded with marketing, and every irrelevant sentence competes for attention in every future AI session.

3. Strategic Goals

Could the client achieve this goal without the system, in principle? If yes, it's a goal. If no, it's a feature — it belongs in the BRD, not here.The sharpest test in this chapter

What breaks downstream: goals that are secretly features get treated as already-decided, skipping the alternatives BRD discovery should explore. Genuinely vague goals give the BRD nothing to check priority calls against.

4. Key Stakeholders

Only people whose involvement affects delivery — not a company directory. Every row needs a named Decision Authority (Final sign-off / Input only / Daily user / End user only).

What breaks downstream: vague Decision Authority means UAT sign-off is ambiguous — you can build a whole sprint and discover the real approver was never identified.

5. Constraints

Hard, non-negotiable limits only. If a constraint can be relaxed with a conversation, it's a preference (Section 6), not here. "None" is a valid, expected answer. Regulatory citations must be specific — "UK GDPR," not "privacy laws."

What breaks downstream: a vague regulatory constraint gives architecture nothing concrete to design against. A genuine preference listed as a constraint locks out options that were actually still open.

6. Technology Preferences

Existing systems that must be integrated with (factual), stack preferences (and how strong), hosting, existing auth provider. "No preference — client defers to delivery team" is correct when true, and should be written exactly that way.

What breaks downstream: omitting an existing integration surface means architecture designs without knowing it exists. Writing a preference as a hard requirement causes over-engineering around a constraint never actually imposed.

7. Success Criteria

Could you check this off during UAT unaided, or would you need the client to say "yes, that feels right"?The template's test

What breaks downstream: vague criteria give /gen-uat-checklist nothing concrete to translate. A bloated list turns UAT into a feature checklist instead of an outcomes checklist.

8. Risks and Open Questions

Two distinct types, never combined: a Risk might go wrong regardless of action and needs mitigation; an Open Question must be answered before a requirement can be written. Every row needs a named owner.

What breaks downstream: an unowned Open Question stays open indefinitely — BRD discovery stalls or proceeds on an unstated assumption. Misfiling a Risk as a Question means it never gets a mitigation plan.

9. Related Artifacts

Auto-populated with the brief as the first row. Known gap: not every generating command keeps this table current automatically — the safest habit is running /update-status after each artifact changes status.

What breaks downstream: a stale entry sends a human — or an AI session — to the wrong version of a document, treating it as current.

Common mistakes ▸
  • Writing the Problem Statement as a feature list instead of current-state pain.
  • Marking a project Extension because it shares a client or similar-sounding domain, not because it can't be understood without the parent.
  • Treating a genuine preference as a Constraint instead of a Preference — silently removing options that were never closed.
  • Leaving Section 8 owners as "TBD" — an easy field to rush past in a live session.
  • Approving the brief and then amending it without running /run-intake in amendment mode — no Document History entry, no audit trail.
  • Hand-filling a brief for a project that actually needed a live client interview — the checklist still technically passes on vague-but-present answers.
