Stage 1

Intake

Everything downstream comes back to one file: brief.md. Rush it, or leave it thin, and the damage doesn't show up until three phases later — a requirement missing a constraint nobody wrote down, or an architecture decision made without knowing a regulation even applied.

What a brief is, and why it gets its own gate

What is a brief? It's a short, plain-language document. It captures what's wrong today, who's involved, what fixing it would achieve, and what limits already exist. It is not a requirements document — it doesn't say what the system will do. It says what the client's actual situation is, before anyone starts designing a solution.

Why does it get its own gate, instead of folding into the first requirements conversation? Because everything downstream treats it as already-settled context. /gen-domain-knowledge won't run until the brief's Content Status is Approved. Once it's approved, every later command — domain knowledge, BRD discovery, architecture — reads the brief's answers as given, not as something to double-check. Get the Problem Statement or Constraints section wrong here, and nobody re-verifies it three phases later. They just build on top of it.

Where does the content in a brief actually come from? Here it's simpler than in later stages: there's no AI-training-knowledge shortcut. A brief is entirely the PO's own answers, about this one specific client. /run-intake doesn't propose a candidate answer and ask you to confirm it, the way domain discovery does — it asks an open question and waits. If you don't actually say something, there's nothing else for it to fall back on.

What actually happens, section by section

The intake session, walked through

Nine sections, filled one at a time, always in the same shape. Before it asks you anything, the session shows you the actual guidance for that section, taken directly from the brief template — not a generic prompt. Then it asks one open question and waits for you to answer freely. If your answer misses something the guidance calls for, it asks one follow-up at a time. Never a list of them at once.

"Describe what's broken or missing today — what the client is living with right now."The actual opening question for Section 1, verbatim

Once you've said enough, it drafts the section and shows you exactly what it plans to write. At that point you get three options, and only three. Approve saves it to brief.md immediately and moves to the next section. Revise takes your feedback and redrafts the same section. Skip leaves it blank and moves on — you can come back to it later.

One more thing happens before Section 1 even starts: the session asks whether this is a standalone project, or one that builds on an existing project. That timing matters — it's asked first, not somewhere in the middle. We cover what the answer actually changes in Standalone vs. Extension, further down this page.

Skip doesn't mean skip forever. If anything is still blank once you've been through all 9 sections, the session stops and reports exactly which sections are pending. Content Status stays Draft, and the brief cannot be Approved until every section is filled. Only once nothing is left blank does the session run its Verification checklist — the same checks behind every "what breaks downstream" warning later in this chapter — and flip Content Status to Brief complete.

Decision heuristic

Project boundary — one product, one project

/init-project uses a simple test: if two things share the same technical pieces — a web app and its own API, say — they're one project. If two things serve different groups of users solving different problems, they're separate projects, even when they happen to share a backend. That one-line rule covers most cases, but three situations trip people up:

"In one sentence, what is this project — what product or capability does it deliver, and who uses it?"The actual question asked, verbatim, before anything is created

If your answer names more than one distinct product, you get pushed back on the spot: "That sounds like more than one product... Which product do you want to start with?" The session won't proceed until your answer describes exactly one.

  • A teacher portal and a parent portal, same school system. These are two separate projects — different user groups solving different problems, even though they might share one backend.
  • An admin dashboard bolted onto an existing product, for the same users. Not a new project — it's new scope inside the one you already have. It belongs in that project's BRD.
  • An admin or ops console built for a different internal team. This is a separate project, and very likely an Extension, since nobody could build or understand it without the parent project's domain knowledge — but it still gets its own brief.
Would this capability have its own go-live date, its own primary user group, and its own BRD sign-off — even if the "host" project never shipped it at all? If yes, treat it as a separate project.The test that generalizes

Project code format, and when to add EXT

Every project gets a code in the format CLIENT-DOMAIN-NNN. You can add an optional fourth segment — CLIENT-DOMAIN-EXT-NNN — but it's purely cosmetic; no command ever reads it. The real extension relationship always lives in the brief's own Project Type, Extends, and Extension Adds fields.

CodeReading
HARBORVIEW-INV-001Harborview, invoice domain, first iteration. A standalone project.
ASCENDRA-PAY-CORE-001Ascendra's own payment product, core layer — the base of an extension chain.
ASCENDRA-PAY-PKN-001The Pakistan market layer on top of the Core project. What actually links the two is the brief's Extends: field, not the code itself.

Running /init-project again on a code that already exists gives you three choices: Cancel, add only the files that are missing, or Reinitialise. Reinitialise overwrites brief.md completely — anything already written there is gone. Everything else (BRD, stories, architecture) is untouched either way. If you're not sure which one you want, Cancel costs you nothing; Reinitialise can't be undone.

Decision heuristic

Standalone vs. Extension — what actually changes

This isn't a cosmetic label. Marking a project Extension changes what gets loaded into context for nearly every command that generates something downstream.

This gets decided right at the start of the session, before Section 1 even opens. The actual question is: "Is this a standalone project, or does it build on top of an existing Ascendra project?" Answer Extension, and you're asked one more thing on the spot: what this project adds on top of the parent, in one sentence.

CommandIf Extension: also loads from the parent chain
/gen-domain-knowledgeParent domain knowledge, base-first — this project's document becomes a delta only
/gen-brd-playbook / /gen-brdParent BRD as baseline — this project's BRD captures only what's new or different
/gen-architectureParent architecture's Extension Points section specifically
/implement-storyParent architecture, to know which codebase/service a story targets
/gen-epics, /gen-storiesNothing — always project-specific regardless of type
Could someone who has never seen the other project fully understand, discover, and build this one from its own brief and BRD alone? If yes, it's Standalone. If they'd be lost without the parent project's context, it's an Extension.The decision test
Decision heuristic

Interactive vs. hand-filled — sizing the session

Small internal project

You're effectively both the PO and the client here. Filling the brief in by hand is usually fine — often faster, too, since there's no vague client answer waiting for a follow-up question to catch.

Medium client project

A real external client is involved, and a discovery call has happened or is about to. Run /run-intake as a live session — its follow-up prompts are what catch a vague client answer before it gets written down as if it were specific.

Large or complex project

A regulated domain, an extension chain, or several stakeholders with different priorities. Always go interactive here — the mandatory Verification checklist is the only thing that reliably forces a check like "does every regulation cite the actual statute."

If you do fill the brief in by hand, still run brief.template.md's Part 2 Verification checklist against your own draft afterward. Nothing else is going to catch its gaps for you.

Resuming, revising, amending

Intake mode (Draft)

Your normal first pass through the brief. Sections run 1 through 9 in order — anything already checked off from a session that got interrupted is skipped, though you're offered a chance to review it first.

Revision mode (Brief complete)

Intake is done, but the brief isn't approved yet. Name the section you want to change, and it re-runs the draft-then-approve loop just for that one.

Amendment mode (Approved)

Any change here is a tracked amendment — a one-line summary appended to a Document History table, with the minor version bumped up. Content Status itself stays Approved throughout.

Density guidance

Section by section: how much is enough

Every "what breaks downstream" warning below traces back to a real, automated check — the same Verification checklist that runs at the end of every intake session, whether you filled the brief by hand or through /run-intake. None of this is a style preference.

1. Problem Statement

Two to four sentences is enough: what's currently going wrong, what it's costing, and what would be true if it were fixed — written from the client's point of view, never as a solution. The two ways this goes wrong are opposite extremes: too thin ("the client needs better invoicing"), or already a solution in disguise ("we are building an automated reminder system").

What breaks downstream: if it's too thin, BRD discovery ends up re-deriving context a discovery call already covered. If it's written as a solution instead of a problem, it quietly steers requirement discovery toward one implementation before anyone gets to explore the alternatives.

2. Client Context

Write enough that someone joining the project halfway through understands the client without asking follow-up questions: who they are, their scale, their current process, and anything that would change a design decision. Company history and mission statements don't belong here — that's a deliberate omission, not an oversight.

What breaks downstream: too thin — no transaction volume, no team size — and neither domain knowledge nor architecture has anything real to scope decisions against. Padded with marketing language instead, and every irrelevant sentence competes for attention in every future AI session that reads this file.

3. Strategic Goals

Could the client achieve this goal without the system at all, at least in principle? If yes, it's a genuine goal. If no, it's actually a feature — and it belongs in the BRD, not here.The sharpest test in this chapter

What breaks downstream: a goal that's secretly a feature gets treated as already decided, which skips past the alternatives BRD discovery should have explored. A goal that's genuinely too vague gives the BRD nothing to check its own priority calls against.

4. Key Stakeholders

List only the people whose involvement actually affects delivery — this isn't a company directory. Every row needs a named Decision Authority: Final sign-off, Input only, Daily user, or End user only.

What breaks downstream: a vague Decision Authority makes UAT sign-off ambiguous later — you can build an entire sprint and only then discover nobody had actually identified the real approver.

5. Constraints

Only hard, non-negotiable limits belong here. If a constraint could be relaxed with a conversation, it's actually a preference, and it goes in Section 6 instead. "None" is a perfectly valid answer. Any regulatory citation needs to be specific — "UK GDPR," not just "privacy laws."

What breaks downstream: a vague regulatory constraint gives architecture nothing concrete to design against. Listing a genuine preference as if it were a constraint locks out options that were actually still open.

6. Technology Preferences

Note any existing systems that must be integrated with (that's a fact, not a preference), stack preferences and how strongly they're held, hosting, and any existing auth provider. "No preference — client defers to the delivery team" is a correct answer when it's true, and it should be written exactly that way.

What breaks downstream: omit an existing integration surface, and architecture gets designed without knowing it's even there. Write a preference as if it were a hard requirement, and you get over-engineering around a constraint that was never actually imposed.

7. Success Criteria

Could you check this off during UAT on your own, or would you need the client to say "yes, that feels about right"?The template's own test

What breaks downstream: vague criteria give /gen-uat-checklist nothing concrete to translate into a test. A bloated list turns UAT into a feature checklist instead of a check on outcomes.

8. Risks and Open Questions

These are two genuinely different things, and they shouldn't get combined. A Risk might go wrong regardless of what anyone does, and it needs a mitigation plan. An Open Question has to be answered before a requirement can even be written. Every row needs a named owner.

What breaks downstream: an Open Question with no owner tends to stay open indefinitely — BRD discovery either stalls on it or quietly proceeds on an assumption nobody actually confirmed. Filing a Risk as if it were a Question means it never gets a real mitigation plan.

9. Related Artifacts

This table starts pre-filled with the brief itself as the first row. One known gap: not every generating command keeps it current automatically, so the safest habit is running /update-status right after any artifact's status changes.

What breaks downstream: a stale entry here can send a person — or an AI session — to an old version of a document and have them treat it as current.

Common mistakes ▸
  • Writing the Problem Statement as a list of features instead of describing the current pain.
  • Marking a project Extension just because it shares a client or a similar-sounding domain — not because it genuinely can't be understood without the parent project.
  • Treating a genuine preference as a Constraint, which quietly removes options that were never actually closed off.
  • Leaving Section 8's owners as "TBD" — an easy thing to rush past in a live session, and easy to regret later.
  • Approving the brief, then amending it without running /run-intake in amendment mode — which means no Document History entry, and no audit trail.
  • Hand-filling a brief for a project that really needed a live client interview. The checklist can still technically pass on answers that are vague but present.
