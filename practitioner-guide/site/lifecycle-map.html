Decision heuristic

Two ways to run this framework

Every stage chapter in this guide is written against typing each command directly, and that stays fully available forever. /anchor-project {PROJECT_CODE} is the other way: one command that resolves or bootstraps a project, then invokes whichever command owns the current stage and runs its instructions exactly as written. Nothing about a command's behavior, file formats, or gates changes depending on which path called it.

What actually changes

Where /anchor-project changes the day, stage by stage

The commands and gates above are identical either way. What anchor removes is different at each region:

Stages 1–5 (Problem Domain): anchor's biggest lift. Five separate PO-facing walkthroughs run back to back — brief, domain discovery, BRD discovery, epic review, screen review. Anchor compresses the question density across all five without skipping any of them, and folds in anything already captured via /run-priming-session the moment each stage needs it.
Stage 6 (Bridge): anchor still invokes /gen-architecture and /review-architecture unmodified — it does not shrink the 34-check review. What it removes is the PO having to know, unprompted, that this is the one stage where a fresh, otherwise-empty session matters most; anchor sequences it that way by default.
Stages 7–11 (Solution Domain): this is where anchor's role visibly narrows once the Walking Skeleton is complete. The per-story loop — plan → implement → verify → PR — reverts to direct command use even on an anchored project, since it runs per story, often across multiple developers in parallel, and doesn't fit anchor's single-threaded sequencing. Anchor returns for release prep (Stage 11) and any formal scope change routed through /assess-change.
Stage 12 (Support): anchor is not driving here by design — this stage is inherently PO/team-run, not sequence-driven.

The Hotfix Cycle

PROJECT-LIFECYCLE.md

Triggered by a Critical or High severity defect found in production. Bypasses sprint planning and UAT entirely — scope is narrow and the fix is validated before deployment: hotfix branch → /implement-story → /verify-story → PR against main → targeted test run (not full E2E) → deploy with rollback plan → smoke tests. PO approval is still required at PR and at deployment — nothing about approval is skipped, only sprint ceremony and full regression.
