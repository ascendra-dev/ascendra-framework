Orientation

How to Use This Guide

CLAUDE.md, SDLC.md, and PROJECT-LIFECYCLE.md tell you what happens and which command runs it. This guide answers a harder question: what do you actually write, how much, and what breaks three phases downstream if you get the judgment call wrong — turning as many of those calls as possible into a test you can apply, backed by a worked example.

Every finding referenced in this guide was verified against the actual command and template files as they exist today, not assumed — the research that produced it surfaced 14 framework defects, all fixed before it was written. Two ways to run everything it teaches: typing each command directly (the default assumption throughout), or via /anchor-project, which invokes the same commands and follows their instructions exactly — it changes the interaction around them, not the commands themselves. A third command, /run-priming-session, is a free-form session that materializes facts into a priming package before formal discovery starts. A fourth, /judgment-check, runs underneath every phase chapter without a section of its own — see Cross-Cutting for full coverage.

Four things that sound related and aren't

Confusing them is easy and the cost is real — you can approve a BRD that's internally consistent under one reading and contradictory under another. Learn this before you touch a real project.

Where they can genuinely conflict: a requirement can be Must Have and Ext:PK at once — Priority says build it first, Layer says you can't yet. Layer wins for build order; Priority governs sequencing within what's buildable right now. If they keep conflicting on a real requirement, that's usually a sign it should be split.

They look related because Layer and the Core/Extension architecture methodology share vocabulary — but Layer is a label on one BRD requirement inside one project, while Core/Extension is how a whole separate future project is architected to build on top of this one. See Harder Cases for a worked extension project exercising both at once.

Distinctions

Other pairs worth knowing before they surprise you

Content Status vs. Status

Status = the whole project's lifecycle, set once. Content Status = one document's own readiness — the field every gate actually checks. Unique to brief.md; every other gated artifact uses one field for both.

→ Intake

Wave vs. Sprint vs. Epic

A wave is what /gen-stories generates against (usually one epic). A sprint is a delivery-cadence unit decided later, purely from story count vs. capacity. One wave ≠ one sprint.

→ Sprint Planning

Portal vs. Screen vs. Surface vs. Pattern

Portal = a nav shell. Screen = one Inventory row, full weight regardless of size. Surface = container (Page/Dialog/Sheet/Drawer). Pattern = internal content shape — independent of Surface.

→ Screen Design

Core/Extension architecture

Layer is a label on one requirement inside one project. Core/Extension is how a whole separate future project plugs into this one. They share vocabulary, not meaning.

→ Architecture
A pattern to watch for across every phase

Scores and thresholds you can't reproduce. Domain Discovery and BRD Discovery both hand you a percentage against a fixed gate (70%, 85%) — but the formula isn't fully specified anywhere, so you can't independently check a number you're handed. Treat any confidence score as a rough signal: read the section it claims is weak yourself, and raise your personal bar above the stated threshold whenever the domain is regulated, unfamiliar, or a wrong assumption costs more than a sprint to unwind. A 70% pass on a niche compliance domain is not the same confidence as a 70% pass on an internal expense tool, even though the gate treats them identically.
