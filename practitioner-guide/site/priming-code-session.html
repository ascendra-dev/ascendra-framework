Priming Code Session

/run-priming-session and this command produce the same output — a priming-package.md — but solve a different problem. A PO narrating their business already knows what matters and why; a legacy codebase has no author in the room to ask, and it accumulated unintentional behavior right alongside its real business rules. This command reverse-engineers business capability from code structure, without ever reading the whole repository. If that sounds like a harder problem than prose priming, it is — keep reading, because this chapter starts from zero.

/run-priming-code-session. Governed by the same contract as Priming Session — read that chapter first.

What's genuinely different about reading code

Why does this need its own command, rather than pointing the prose-priming session at a code file? Two problems that prose priming never had to solve. First, telling a real business rule apart from an accident — a human writing prose has intent behind every sentence; code accumulates unintentional behavior too, with nobody around to ask which is which. Second, chunking a codebase too large to read in full, without silently presenting a guess as if it were precision.

Where does its output go? The same priming/priming-package.md its prose sibling writes to — read by the same three later commands. But this command also keeps its own working-state file, code-priming-state.md, tracking progress unit by unit so a large codebase walk can checkpoint and resume any number of times.

Does it need the PO in the room? Not the way prose priming does. A codebase doesn't need someone narrating it, and this command is built to walk one unattended across many checkpointed sessions. A live PO is still useful for resolving flags cheaply and narrowing scope up front, but continuous presence isn't required.

Preferred, not assumed

Entity-centric chunking, with honest degradation

The Map pass is structural only — no file contents read yet. It walks the directory structure, and for each module looks for recognizable schema or ORM patterns: an annotated entity class, a models file, a schema definition, a migration file. These are framework-agnostic concepts, not stack-specific rules — recognizing them is ordinary pattern-reading in any language.

Entity layer discoverable

Chunking proceeds entity by entity — the finest, most useful granularity.

Entity layer not discoverable

Attempt entity inference within the module first — including from table names in raw SQL strings. Only when boundaries genuinely can't be found does it degrade to Module/Layer granularity.

A module-level row is never dressed up as an entity-level one. If the walk couldn't find the boundary, the record says so — in the Entity Ledger's own Granularity column.Honesty over false precision
The problem prose priming never had to solve

Telling a rule from an accident

A human writing prose had intent behind every sentence. Code accumulates unintentional behavior too — the walk has to guess which is which from the evidence in front of it.

✓ Leans toward a real rule
Enforced redundantly across layers (DB constraint + application validation + UI disabling an action). A business-language error message. Named consistently across unrelated parts of the codebase. Traceable to a comment or commit citing a business reason.

A candidate for AI Knowledge Correction if it diverges from generic domain understanding.

✗ Leans toward a legacy flaw
Inconsistent enforcement — checked on one path, skipped on another. An unexplained magic number, or a HACK/TODO marker. Contradicts what's generically true elsewhere. Duplicated data with no stated reason.

A candidate for Legacy Design Question — never carried forward as fact, always a negotiation.

If a PO happens to be live during the walk, ask directly — cheaper resolution than deferring to a flag. If no PO is present — the expected default here, unlike prose priming — the flag waits for whichever later session actually reads it.

Not every unit has all seven

Signal sources, ranked by trust

RankSignalWhy
1Schema/ORM definitionsHighest trust — entities, lifecycle states, relationships
2Validation logicGuards, DTO decorators, DB constraints
3State machinesEnums plus transition guards
4Test names and assertionsFirst-class, not a fallback — often clearer than the implementation
5Comments and commit messagesCross-checked against current behavior, since comments rot
6Feature flags / per-tenant configMaps directly onto Known Variations
7API surfaceMedium signal — can be generic scaffolding

The ranking matters because it tells you which signal to trust when two disagree — a schema constraint outranks a stale comment; a test assertion outranks an API route that might just be boilerplate.

The one real exception

The two subsections this command actually owns

Its prose sibling owns no Section 10 (Source-Specific Material) subsection at all — everything it extracts maps onto Sections 4–6. This command is the exception, and owns two.

Code Structure Reference

Existing API surface and schema-as-implemented. Captured only incidentally while extracting for domain purposes — never pursued on purpose. Priming is scoped to Problem Domain only; going looking for this on purpose would mean quietly doing architecture's job early.

Sub-Domain Split Recommendation

A non-binding note, derived from the code's own module boundaries, that the eventual domain document(s) may need splitting. Routes specifically to /run-domain-discovery — the one case in this framework where a priming artifact names its own destination phase.

Per unit, not per session

Progress lives in a dedicated working-state file, code-priming-state.md, kept distinct from priming-package.md itself — the same relationship a discovery-state file has to its own finished artifact. Every unit's row is written to Extracted immediately after it finishes, before moving to the next one. The ledger, not conversation history, is what makes a large codebase resumable — a genuinely large file taking more than one session to fully triage is normal, not a sign something went wrong. Do not hold more than one unit's extraction in working context at a time; resist the urge to batch several units together to save a round trip.

Terminology recap
  • Domain-likely vs. infrastructure-likelyWould every deployment need this, regardless of extension? Infrastructure gets one boundary note; domain-likely proceeds to full Extract.
  • Entity vs. Module/Layer granularityRecorded explicitly, never silently upgraded. Module/Layer is an honest admission, not a shortcut.
  • code-priming-state.md vs. priming-package.mdA working ledger vs. the actual PO-facing deliverable. Only the priming package is read by later commands.
Common mistakes ▸
  • Reading a module's whole "home" directory instead of a targeted search for the unit's own name and references.
  • Presenting a Module/Layer-granularity result as if it achieved entity-level precision.
  • Carrying forward an inconsistently-enforced rule as fact instead of flagging it as a Legacy Design Question.
  • Trusting a comment over a schema constraint when the two disagree.
  • Going looking for architecture-flavored facts on purpose instead of noting them only when they surface incidentally.
  • Batching several units' extraction together instead of checkpointing after each one.
  • Treating the Sub-Domain Split Recommendation as a decision this command makes, rather than a note for /run-domain-discovery to weigh.
Harborview in practice

Be honest about what's actually here: Harborview's domain was judged well-known enough to skip even the prose priming sub-flow's deepest path, and no legacy codebase was ever part of its worked material — there's no code-priming-state.example.md in this repository, and this command hasn't yet been validated against a real legacy walk. That's a real, stated gap in the framework itself, not something glossed over here.
