Stage 8

Development

Four commands run in sequence, once per story, for the life of the project: plan, implement, verify, describe. It's tempting to read that as three commands' worth of real work plus one bookkeeping step bolted on the front — it isn't. /gen-story-plan exists because a PO explicitly asked to see what a story would produce before implementation started, not find out after the fact. That's why /implement-story hard-gates on the plan being Confirmed, with no override — the plan is cheap enough to produce and review that there's no legitimate "not worth it" case. If that sounds like process for its own sake, keep reading — this chapter starts from zero.

/gen-story-plan, /implement-story, /verify-story, /gen-pr-description. Assumes stories are already Reviewed and sprint-assigned per Chapter 7.

Start here

Four commands, one story, always in the same order

What happens in this stage? Once a sprint is Active, every story runs through the same sequence. /gen-story-plan states what gets built — which endpoints, tables, screens, or jobs, in what order, tested how — extracted from the already-Locked architecture and the story's own acceptance criteria. /implement-story states how to build it, in this project's confirmed stack idiom. /verify-story checks the result against the plan's own test scenarios. /gen-pr-description writes up the PR from what actually changed. A plan never invents architecture — anything the architecture doesn't already define is a gap flagged in the plan's own Risks section, not a decision made on the spot.

Why does the plan get its own gate, separate from the story itself? A story's acceptance criteria describe what the user experiences — not which endpoint, which table, which screen. The gate this buys you is unusually strict for this framework: /implement-story hard-gates on the plan being Confirmed, with no PO override — unlike the softer dependency-cleared and Open-Decision gates in the same command, which do allow one. That strictness was a deliberate choice, not a default: a plan is materially cheaper to produce than a BRD or architecture document, so there's no legitimate "not worth it for this story" case.

Where does a story plan's content come from? Entirely extracted from the already-Locked architecture document — the exact endpoints, tables, and screens this one story needs, filtered down to just its own scope. Nothing in a plan is invented; it's the architecture's own facts, narrowed to one story.

The real gate isn't Step 9

The story-plan confirmation checklist

Step 9's summary asks "does this plan structure look right?" — that's a structure check, not a content review. It confirms every AC has a row, not that the row is right. And the plan is written with Plan Status: Draft regardless of how you answer — the actual decision happens afterward, against the written file, via update-status ... Confirmed. That's the moment this checklist is for, after you've opened the real file and can read the API/Web/Worker blocks, not the one-line summary.

Check againstAsk yourself
Each API block's Auth lineDoes the guard/role match who you'd actually expect — not a plausible placeholder?
Each API block's Queries lineIs tenant-scoping present when this project has a tenant boundary?
Each WEB block's Route/SurfaceDoes this match the approved mock — same path, same Page/Dialog/Sheet/Drawer?
Each WEB block's Data layerDoes the hook name and the API call it references actually line up?
AC → Artifact TraceabilityDoes every AC map to something that genuinely satisfies it?
Risks / Open QuestionsAnything you'd resolve differently than proposed?

If any answer is "no" or "I'm not sure," that's a Change through the normal review conversation with the AI, applied before you type Confirmed — not a note to fix during implementation.

A plan you correct after implementation started costs the same re-implementation chain a wrong architecture decision does — just scoped to one story instead of the whole system.

What to expect on first touch

Repo scaffolding, and why the diff looks so big the first time

/implement-story bootstraps a repository the first time any story touches it. Nothing upstream of that — not the gate-check messages, not the story plan — tells you in advance that this is coming, so say it plainly before you hit it: if this is the first story for a given repo, expect the diff to include an entire scaffolded project, not just this story's own endpoint or screen.

A one-endpoint story can produce a diff touching dozens of files once you count the module structure, the global exception filter and structured logging, the frontend auth session module and typed API client, the test tooling, and the .env.example. That's expected bootstrap work — the first story is quietly paying down a setup cost every later story in the same repo won't have to — not scope creep, and not a sign the AI over-built the story.

This doesn't get hidden from you either: /gen-pr-description's own diff-fidelity discipline means a first-touch PR's "What Changed" section will honestly list the scaffold alongside the story's own work, rather than inferring a smaller change from the ACs alone. Read that as the safeguard it is — if a later story on an already-scaffolded repo produces a similarly oversized diff, that's the actual signal worth chasing.

Finer-grained than scaffolding

Vendoring an ascendra-commons module

Only relevant if the project adopted a module during architecture — check standards/ for a *-pattern.md file citing ascendra-commons; if none exist, this doesn't apply. Where repo scaffolding happens once per repo, vendoring happens at a finer grain: the first story that needs a specific adopted module — not the whole project, and not at repo-bootstrap time — triggers copying just that module's packages into src/ascendra-commons/{module}/.

A Model 1 adoption typically needs {module}.core plus its Model 1 family package; some modules also need .api consumed directly even under Model 1, if the module's own README names it explicitly. A project that adopted 2 of the 15 modules never touches the other 13. If a later story needs the same module, /implement-story checks whether it's already vendored and skips — once per module, not once per story that touches it.

What to expect in the diff: the first story that vendors a module produces a separate commit, chore: vendor ascendra-commons/{module}, kept apart from the story's own commit — mirroring how a Web repo's ascendra-ui scaffold commit is kept separate too. Look for that commit specifically when reviewing a PR that's the first to touch a module.

The .core-only rule, at the level you'll actually see it: every import from a vendored module in this project's own code should resolve to that module's .core package — never a concrete implementation package reached past it for convenience. You don't have to catch this yourself line by line; it's one of the things /implement-story's own Standards Compliance Self-Check re-reads against the actual diff before reporting a story done, "not from memory of what was written earlier in the same session." If a PR's diff shows a direct import reaching past .core where it shouldn't, that's the same class of defect that compiles, lints, and passes tests cleanly regardless — worth a second look specifically because nothing automated catches it.

The asymmetric recovery loop

What to actually do when something fails

/implement-story and /verify-story fail in genuinely different ways, and the framework only gives you a clean procedure for one of them.

Implementation failure

Clear and bounded: "if you cannot fix a failure after two attempts, report it explicitly — state exactly what failed and why." Two tries, then it stops and tells you. You always know where you stand.

Verification failure

No stated procedure — the failing-AC message just says "resolve these before raising the PR." The instinct to re-run /implement-story is wrong: a story that's already been implemented is In Progress, and that command's own gate check requires Reviewed. It hits the gate and refuses.

The actual recovery path: fix directly on the same story branch — edit the code yourself or direct the AI to make the specific correction, re-run lint/build/test, commit — then re-run /verify-story against the fix. You're not re-planning or re-scaffolding; you're correcting code that already exists on a branch that already exists.

If the same AC fails verification twice in a row, that's a plan-correctness signal, not an implementation-effort signal. A misread requirement, a wrong endpoint assumption, a guard name that doesn't actually exist — these are plan-level errors that no amount of re-fixing the code will resolve, because the code is faithfully building the wrong thing. Stop attempting a third blind fix. Regenerate the plan instead — a new Document Control row, Plan Status reset to Draft — walk through what changed against the checklist above, confirm it again, and only then resume implementation.

Two real template mismatches

Where the templates and commands currently disagree

The framework's generating commands and their templates are supposed to agree. Two places in this stage they currently don't — worth knowing since neither file flags the other.

Story-plan template's Data Layer field

The template's placeholder literally names React Query: "[React Query hook name], [query / mutation], calls [API-N above]." But the command's own instruction is the correct, conditional one — if the confirmed approach is hookless (e.g. Server Components only), describe the real fetch mechanism instead, never assume React Query. There's no worked hookless example in the example file to copy from — expect to improvise the format the first time you hit one.

PR description's Pre-Merge Checklist

Two items hardcode orgId-from-JWT and React-Query-cache-invalidation as plain, unconditioned checklist lines — exactly the kind of unconditional assumption the framework's own stack-agnostic principle bans everywhere else in this stage. On a project with a different tenancy scheme or no React Query, tick "— N/A" honestly rather than forcing a match that doesn't describe what the diff does — the template's own guidance for an inapplicable item already tells you to do exactly this.

What "stack-agnostic" means at run time

/implement-story reads the architecture document's Section 2 before doing anything else — NestJS/Next.js is a reference path for the common case, never a hardcoded universal rule, even though it's the framework's common default and the stack Harborview itself confirms. Every stack-specific instruction is explicitly conditioned, with a stated fallback to apply the same underlying principle using whatever framework the project's own architecture document documents.

If you're running this against a project confirming a Java/Spring backend or an Angular frontend, don't be alarmed when the command's own internal reasoning names spring init and a @RestController annotation instead of NestJS's idioms — NestJS was never the "real" standard, just the worked example this framework's own home project happens to use. The command working correctly on a non-default stack looks exactly like it not following the NestJS/Next.js content in this chapter — that's the intended behavior, not the command drifting from something it should have followed.

Terminology recap
  • Plan Status vs. Story StatusA story can be Reviewed while its plan is still Draft — two independent gate fields. /implement-story checks the plan's Plan Status, not the story's Status, for its own gate.
  • Target (API/Web/Worker)Set once, at /gen-stories time, from the Locked architecture's repo topology. Every later command cross-checks it rather than re-deriving it.
  • Plan ConformanceThe section /verify-story adds, comparing what the plan declared against what was actually delivered. A documented deviation is a Match-with-rationale, not a Defect; an undeclared one is.
  • Scaffolding vs. vendoringScaffolding: once per repo. Vendoring: once per ascendra-commons module. A repo can be long-scaffolded and still vendor a new module on story forty.
  • Deviations from PlanWhere /implement-story records any point it had to diverge from the Confirmed plan, and why. Blank at generation; filled in only if execution genuinely needs to depart.
Common mistakes ▸
  • Typing Confirmed off the Step 9 summary table instead of opening the written plan file.
  • Panicking at an oversized first diff on a repo's first story.
  • Re-running /implement-story to fix a verification failure — it hits the status gate.
  • Attempting a third blind implementation fix instead of regenerating the plan.
  • Copying the Data Layer field's React Query wording literally on a hookless project.
  • Forcing a Pre-Merge Checklist match on a project that uses neither orgId nor React Query.
  • Reading a non-NestJS/Next.js idiom in the command's reasoning as a defect.
  • Confirming a plan without checking its Auth, Queries, Route, and Data-layer lines against what you actually remember agreeing to during architecture review.

story-plan.example.md — US-01-002

Run the checklist above against it directly: the Auth line on API-1 (JwtAuthGuard, @Roles('finance_manager')) names the exact role you'd expect for invoice creation. The Queries line ("insert scoped to caller's orgId") shows tenant-scoping present. WEB-1's Route (/invoices/new) and Surface (Page, Screen ID SCR-014) match a real screen ID rather than an invented path.

WEB-1's Data layer (useCreateInvoice mutation hook, calling API-1) is the React Query case the template's field wording was written for — contrast this against the hookless case, which you won't find worked out anywhere in this file. Section 5 (Risks / Open Questions) is honestly "None." here — a real instance of a plan with nothing left to flag, not every plan you write will be this clean.

pr-description.example.md — US-01-001

Shows the template's own N/A instruction already in honest practice on the two hardcoded checklist items: orgId from JWT ticked "— N/A (migration only, no API endpoint)," and React Query cache invalidation ticked "— N/A (backend-only PR)." This is the exact move to make on your own project whenever either item genuinely doesn't apply to what the diff does.
