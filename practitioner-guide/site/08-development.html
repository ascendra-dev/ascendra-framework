Start here

Four commands, one story, always in the same order

What happens in this stage? Once a sprint is Active, every story runs through the same sequence: /gen-story-plan figures out what the story will actually touch — which pages, endpoints, and queries — before any code is written. /implement-story writes the code, exactly to that plan. /verify-story checks the result against the plan's own test scenarios. /gen-pr-description writes up the PR from what actually changed. This repeats once per story, for every story in the sprint.

Why does the plan get its own gate, separate from the story itself? A story's acceptance criteria describe what the user experiences — not which endpoint, which table, which screen. FW-031 exists because the PO explicitly wanted to see what a story would actually produce before implementation started, not find out after the fact. That's why /implement-story hard-gates on the plan being Confirmed, with no override — the plan is cheap enough to produce and review that there's no legitimate "not worth it" case.

Where does a story plan's content come from? Entirely extracted from the already-Locked architecture document — the exact endpoints, tables, and screens this one story needs, filtered down to just its own scope. Nothing in a plan is invented; it's the architecture's own facts, narrowed to one story.

The real gate isn't Step 9

The story-plan confirmation checklist

Step 9's summary confirms every AC has a row, not that the row is right. The actual decision happens after, against the written file, via update-status ... Confirmed.

Check againstAsk yourself
Each API block's Auth lineDoes the guard/role match who you'd actually expect — not a plausible placeholder?
Each API block's Queries lineIs tenant-scoping actually present when this project has a tenant boundary?
Each WEB block's Route/SurfaceDoes this match the approved mock — same path, same Page/Dialog/Sheet/Drawer?
Each WEB block's Data layerDoes the hook name and the API call it references actually line up?
AC → Artifact TraceabilityDoes every AC map to something that genuinely satisfies it?
Risks / Open QuestionsAnything you'd resolve differently than proposed?

A plan you correct after implementation started costs the same re-implementation chain a wrong architecture decision does — just scoped to one story.

What to expect on first touch

If this is the first story for a given repo, expect the diff to include an entire scaffolded project — module structure, exception filter, logging, auth module, .env.example — not just this story's own endpoint. That's expected bootstrap cost every later story won't pay, not scope creep. If a later story on an already-scaffolded repo produces a similarly oversized diff, that's the actual signal worth chasing.

Finer-grained than scaffolding

Vendoring an ascendra-commons module

Only relevant if the project adopted a module during architecture. Vendoring happens once per module, at whichever story first needs it — not once per repo, and not for every adopted module up front. Look for a separate chore: vendor ascendra-commons/{module} commit, kept apart from the story's own work.

Every import should resolve to that module's .core package — never a concrete implementation package reached past it for convenience. This is one of the things /implement-story's own Standards Compliance Self-Check re-reads against the actual diff, "not from memory of what was written earlier in the same session."

The asymmetric recovery loop

Implementation failure

Clear and bounded: two attempts, then it stops and reports exactly what failed and why. You always know where you stand.

Verification failure

No stated procedure. The instinct to re-run /implement-story is wrong — it hits the In Progress gate and refuses.

The actual recovery path: fix directly on the same story branch, re-run lint/build/test, commit, then re-run /verify-story.

If the same AC fails verification twice in a row, that's a plan-correctness signal, not an implementation-effort signal. Stop attempting a third blind fix. Regenerate the plan instead.

Two real template mismatches

Story-plan template's Data Layer field

Hardcoded to React Query language. The command's own conditional instruction is correct — on a hookless project, describe the real fetch mechanism instead. No worked hookless example exists to copy from.

PR description's Pre-Merge Checklist

Two items hardcode orgId/React Query as unconditional. Tick "— N/A" honestly on a project that uses neither, rather than forcing a match.

What "stack-agnostic" means at run time

/implement-story reads Section 2 before doing anything else — NestJS/Next.js is a reference path for the common case, never a hardcoded universal rule. Seeing a Spring or Angular idiom in the command's own reasoning on a non-default project is the intended behavior, not the command drifting from a "real" standard.

Terminology recap
  • Plan Status vs. Story StatusA story can be Reviewed while its plan is still Draft — two independent gate fields.
  • Scaffolding vs. vendoringScaffolding: once per repo. Vendoring: once per ascendra-commons module. A repo can be long-scaffolded and still vendor a new module on story forty.
Common mistakes ▸
  • Typing Confirmed off the Step 9 summary table instead of opening the written plan file.
  • Panicking at an oversized first diff on a repo's first story.
  • Re-running /implement-story to fix a verification failure — it hits the status gate.
  • Attempting a third blind implementation fix instead of regenerating the plan.
  • Copying the Data Layer field's React Query wording literally on a hookless project.
  • Forcing a Pre-Merge Checklist match on a project that uses neither orgId nor React Query.
  • Reading a non-NestJS/Next.js idiom in the command's reasoning as a defect.
