Harder Cases

Harborview is deliberately the easy path — one client, one well-understood domain, one portal, Core layer only. That's exactly why it can't teach the judgment calls that actually cause trouble. Targeted vignettes, not a second project traced end to end.

Case 1 — Cross-border remittance compliance

A licensed money-transfer operator sending remittances UK → Pakistan, Philippines, Nigeria. The self-test from Domain Discovery, applied for real:

  1. Name the 3 most consequential rules confidently? You can guess "large transactions need checks" — not the actual threshold or regulator. Low confidence.
  2. Wrong assumption costs >1 sprint? Yes — a regulatory exposure, not a UI bug.
  3. Regulator that would reject wrong output? Yes, several, disagreeing across corridors.

Where Section 5 vs. 10 gets concrete: "transactions over $3,000 require enhanced due diligence" sounds universal. It's actually the US FinCEN threshold — the UK's MLR threshold differs, Nigeria's CBN threshold differs again. This belongs in Section 10 (Known Variations), never Section 5 — get it wrong and the framework won't ask which threshold applies in any corridor.

What the raised 90% bar looks like here: every regulation in Section 9 cited to something specific ("UK MLR 2017 Regulation 33," not "AML regulations apply"); every Section 12.3 Unverified row treated as a hard blocker; a Known Variations row for every corridor with its own confirmed threshold, not one row saying "varies."

Case 2 — Ascendra Pay's Pakistan extension

ASCENDRA-PAY-001

The base platform. Standalone. BRD §1.6 names two extension dimensions (Market: Pakistan; Sector: School) — naming them signals where architecture leaves seams, without designing the extension yet.

ASCENDRA-PAY-PKN-001

The Pakistan extension, its own project, its own brief. Extends: ASCENDRA-PAY-001 — a free-text sentence, the field that actually drives every downstream chain resolution.

What Layer looks like here, in contrast to Harborview's all-Core BRD: "capture a 7-digit NTN for every Issuer" is tagged Ext:PK — a UK retailer wouldn't need it. "Generate an invoice PDF" stays Core regardless of which project's BRD it's written in.

Layer and Core/Extension architecture meet, and stay separate: Layer labels this project's own requirements. The Core/Extension methodology is what the base project's architecture already built to make the seam exist. If a PO on the extension project finds themselves needing to change something in Core, that requirement doesn't belong to this project — it's a change request against the base, through /assess-change there.

Case 3 — Multi-portal RBAC: the School extension

School Admin and Bursar (same SSO, same app, differ only by visibility) vs. Parent (standalone magic-link, has never touched the school's Google Workspace).

The base portal rule fails immediately for Admin/Bursar vs. Parent — before nav items even matter, they don't share an authentication flow. Two portals, full stop.Applying the Screen Design boundary test

Where RBAC bites past the portal boundary: a Parent must see only their own children's fees — two parents with legitimate access to the same student is the normal case, not an edge case. This isn't a Screen Design decision (that's Architecture's Section 6, a per-row data-scoping rule) — but Screen Design is responsible for modeling the Family Portal's data requirements as scoped-by-default ("this Parent's children's fees," not "fees") so Architecture confirms a requirement already surfaced, rather than discovering it from scratch.
