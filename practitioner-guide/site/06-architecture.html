Stage 6

Architecture

The densest phase in the framework — the last artifact with no code behind it, and the first one every later command treats as literal, binding fact. /review-architecture's own framing says it plainly: "every table name, column, endpoint, auth rule, and enum value becomes law for every story and every line of code." Get a judgment call wrong here and the correction chain runs BRD update → architecture revision → story updates → re-implementation → re-verify → re-PR → re-UAT — the most expensive path in the whole framework. If that sounds intimidating, it should focus your attention, not your anxiety — most of this document is either derived for you or structurally checked. This chapter is about the handful of places that genuinely need your judgment.

What architecture is, and why it's the one hard bridge in the framework

What is architecture, in this framework? It's the single document that decides every technical fact the system will be built on: the tech stack, the full data model, every API endpoint and its contract, the security and permissions model, infrastructure. Nothing before this stage has depended on any of it — the BRD, epics, and screen design were all written without knowing what database or framework would be used.

Why is this the one stage everything else waits on? Every stage before this one has zero architecture dependency, by design. This is the first hard dependency point: nothing in Stories, Development, Testing, or Release can start until this document is Locked. That's a structural boundary the framework draws deliberately, not just a process preference.

Two commands, two jobs, same split as Epics. /gen-architecture derives and proposes — reading the approved BRD, epics, domain knowledge, and Screen Design, then deriving everything else by asking you directly. /review-architecture runs a 35-check structural audit across five concerns before you lock the document. This chapter is about the judgment calls embedded in both — several of which are dense, bundled into compound confirmations, or resolved by heuristics the command never surfaces as a decision point at all.

Process decision — before the command runs

What to prepare beforehand, and what the command figures out on its own

Pre-authoring standards/ is optional, not required — despite how CLAUDE.md's Workspace Setup reads. /gen-architecture works from a completely empty standards/ folder by default: Steps 4 through 7 derive the tech stack, the architecture pattern, and every standards file conversationally, presenting what it derived and asking only what it can't infer. A first-time PO who reads CLAUDE.md literally and tries to hand-write api-standards.md or security-standards.md from a bare template before running the command is doing work the command will do for you, against a template with no worked instance to calibrate against.

Pre-authoring earns its keep in exactly one situation: you have a hard, non-negotiable mandate — an existing cloud vendor contract, a database the client has already paid for, a compliance requirement that rules out an option the AI might otherwise recommend — and you want it locked in before the AI proposes something else and you have to walk back a recommendation mid-conversation. If that's your situation, write only the file carrying that mandate; the command reads whatever exists and asks whether to proceed with it rather than silently overwriting it.

If you do want to hand-author something, or want to sanity-check a generated file against a real bar, two worked examples exist for exactly this:

technical-standard.example.md

Harborview's api-standards.md — cites the fixed wire contract rather than restating it, a Correct/Incorrect pair for the rule generation gets wrong most often, and one complete controller/service/DTO example applying every rule together.

architectural-pattern.example.md

Harborview's idempotent Stripe webhook handling — a genuinely warranted Tier 3 document (money-moving, externally-triggered, retry-prone), not a generic "might be useful" addition.

Both are dense in the same way REQ-002 was dense in Chapter 3 — every sentence is doing real work, not padding a template out to look thorough. That's the bar to calibrate against.

Optional, stack-gated

ascendra-commons module adoption

Applies only when the confirmed backend is NestJS + Drizzle on Postgres or Supabase — full stop, no partial match, no "translate the concept" fallback for a different stack. Most projects will never see it mentioned anywhere in their own output, and that's the expected, correct outcome, not a gap. When the gate does pass, each of the fifteen modules is evaluated on its own against a real BRD or domain-knowledge signal — never as a package deal. Declining a module is as normal an outcome as adopting one; most projects on the matching stack still adopt only a handful of the fifteen.

What you're actually confirming when a module shows up

Don't read a module row the way you'd read a routine baseline standard generated whether you engage with it or not. What's actually being decided isn't just whether to adopt the module — it's which Model. Every module's own README states plainly what its Model 1 ships and the concrete trigger for Model 2, and the command reads that README to settle the question against this project's actual scale, not a guess. That's exactly the kind of choice worth asking "why this and not the other" about before you confirm — the same instinct this chapter already asks you to apply to the stack table below, and for the same reason: a module-adoption row is a baseline-forming confirmation too.

Why the generated file cites, rather than invents

A module's standards file follows the same shape as any project-invented pattern document, but its content is read directly from the real module's README and cited, not re-derived — the same "cite, don't restate" discipline api-standards.md already applies to the fixed API contract. The generated file also records which ascendra-commons commit or date that README was read at, because the library has no release or versioning tooling yet — without a frozen reference, a later change to the source repo could make an already-Locked project's citation silently stale. This is the same discipline that already governs this project's own architecture document versioning.

Every module's public surface is its .core package. Everything past that is an implementation this project's own code never imports directly — the seam that lets a future Model 1 → Model 2 swap happen without touching business logic.The one rule worth remembering

Where this doesn't show up: Harborview itself is stack-neutral by design — its architecture never confirms NestJS + Drizzle as excluding some other option, so it never exercises this gate at all, and none of its example files show an adopted module. There's no Harborview instance to point you to here; treat that absence as accurate, not as something missing from this guide.

A schema decision disguised as one bullet

Actor Identity Shape

Step 4 derives five things together and asks four explicit questions in the same breath — Actor Identity Shape is the fifth derivation, not one of the four questions, which makes it easy to read past as background noise rather than a decision you're being asked to make.

What's actually being decided: every Master table in the system — invoices, payers, staff records, every primary domain record — carries audit columns for who created, updated, and deleted the row. There are two shapes for those columns, and only one is right for a given project:

A clickable reference

A uuid foreign key into one user table. Works only if every actor in the system is the same kind of authenticated, in-tenant user.

A plain name string

A varchar, no foreign key. Required the moment there's more than one kind of actor — an authenticated staff member, a customer who only ever clicks a one-time emailed link, and a scheduled background job all need to show up in that field, but only one of them has an account to link to.

A single link-style field can't point at three different kinds of actor at once — for any action taken by the second or third kind, the column would just silently be NULL. Getting this wrong isn't caught by any later check: /review-architecture check 18 only confirms the mandatory audit columns exist, not that their shape is right for this project's real actor population. Fixing it later isn't a config flag — it's a migration touching every table in the schema that tracks who-did-what, project-wide, all at once. The full reasoning, including why a third option (a type-discriminator column) was considered and rejected on cost grounds, lives in FW-037 — but nothing in the command surfaces that reasoning to you in the moment. Stop on this line separately from the four questions below it; it deserves its own moment of attention, not a nod on the way past.

What Section 9 structurally cannot catch

Deviation detection's blind spot

Section 9 (Deviation Declarations) flags anything in the architecture document that differs from standards/system-architecture.md. That's a genuinely useful mechanism for catching later drift — someone hand-edits the document after generation, or a standards file gets updated and the document doesn't follow. /gen-architecture's own Step 3 (Standards Drift Check) exists specifically for that case, and it works.

If you're not sure why a row was recommended, ask "why this and not X" before you confirm, not after.The only real guardrail

The only real guardrail on the twelve-row stack confirmation is your own attention in the moment it's presented. Nothing downstream re-litigates it — not /review-architecture, not a later Section 9 flag, because by design it can't.

A silent fork off BRD wording

Composable capability detection

Here's the concrete question hiding behind the jargon: can someone be handed the single permission "approve invoices" without also being made a full Director — or does every permission only ever come bundled into a fixed role like Director, Finance Manager, Staff? Section 6.1 answers this by scanning the BRD for phrases like "independently assignable" — and if it finds a match, that one word quietly switches the entire shape of how login sessions carry permissions, and every access check built on top of it. It's decided once, silently, by pattern-matching a phrase, and it only resurfaces as an already-settled fact later, when Concern D frames it during review.

What to do: check it against your own memory of how the client actually described permissions during discovery. If the BRD says a Staff member can be granted two capabilities independently and the framing says composable, that's correct. If the framing says composable off a looser phrase that doesn't really mean independent assignment, say so before Concern D closes — reversing this after stories are written means rewriting every access check in the system, not editing one sentence.

Using the review without redoing the AI's work

What's genuinely reviewable vs. what you're meant to trust

The 35 checks run off-screen — you see "no flags," not the work. You cannot independently verify that without re-deriving every REQ-to-table mapping and every column list yourself, which is exactly the work the review exists to do for you. Give yourself permission to stop trying to parse Drizzle schema blocks and DTO decorators you're not equipped to audit, and redirect that effort to the parts actually written for you.

How to engage with each concern: read the "Frame this concern" paragraph in full every time — it's written to be understood without engineering background, and it's the thing most worth your attention. When FLAGS come back empty, don't take that as proof nothing's wrong — take it as "nothing the structural checks are built to catch is wrong." Spend your real attention on the targeted PO question at the end of each concern — the plain-language checkpoints built for exactly the kind of gap a structural check can't find, things like "is there a capability you discussed with the client that doesn't have an obvious home."

If something feels off and "no flags" doesn't sit right, ask the AI directly which specific check numbers ran for that concern and what each found — the checks are numbered and documented, and nothing stops you from asking for the receipts on any one of them. Use that when a summary feels too clean, not as a routine step on every concern.

The lock confirmation now captures an optional rationale — reply lock: {what you specifically verified}, or a bare lock with no rationale; both are accepted. Given what locking commits you to, that sentence is worth writing — it's what you point back to later if a decision gets questioned mid-project and nobody remembers exactly what was checked before the document became binding.

Genuinely PO-readable, most POs never find out

Core/Extension methodology

Would every deployment of this base system need this, regardless of which extension is active? If yes → Core. If no → Extension.The Membership Test — two sentences, run it yourself

Concern A's framing gives you a one-sentence summary per extension point — enough to confirm the table exists, not enough to judge whether the seam is drawn in the right place. Don't stop at the summary. Open the reference document yourself and apply the Membership Test to the least-obvious seams — the ones where you're not immediately sure why something landed on the Core side of the line rather than the Extension side. It reads in minutes and the test is yours to run, not something you need an architect to run for you.

For a worked instance against a real, non-Harborview project, see Harder Cases' Case 2 — the Ascendra Pay Pakistan extension — which walks the boundary test against a real Core/Extension split, rather than Harborview's single, unexercised extension point.

The honest limit

"No undocumented deviations" is enforced by your own review, not a standing structural gate. Locking makes the document binding in principle — it creates no command that continuously checks real running code against it. The evidence is a repeated pattern across three separate decisions, each describing the same failure shape:

  • FW-033 — the standard specified JWKS token verification; the implemented code used a shared-secret check instead. Caught only when a real login failed in practice, not by any structural check.
  • FW-040 — five separate UI-implementation gaps found only by manually comparing implemented screens against real component source.
  • FW-041 — a documented global exception filter and structured logging that existed nowhere in the actual codebase, for months, on a live project. Found by manual review, not by any test, lint, or gate.

In every case, the standard said X, the real code did something else, and the gap was closed by a person reading source code directly or a real failure forcing the issue — never by a command whose job was to confirm running code still matches the Locked document. Spot-check real code against the Locked document periodically — at sprint boundaries is reasonable. There is no command that does this for you.

Terminology recap
  • Actor Identity ShapeFK into one user table, or a self-contained actor-label string — required the moment there's more than one kind of actor.
  • Deviation (Section 9)Only catches drift after the baseline exists — structurally cannot flag a bad choice made in the same confirmation that produces the baseline.
  • Composable capability modelThe capabilities: string[] JWT shape, used instead of a single role: string when the BRD describes permissions as independently assignable. Detected automatically from wording — confirm it against your own memory of the actual conversation.
  • Standards Tiers (1–3)Classify a generated standards/ file: Tier 1 baseline (every project), Tier 2 per confirmed technology, Tier 3 AI-determined project-specific or ascendra-commons patterns.
  • Fix tiers (1–4)The same pattern as /review-epics, reused here: Tier 1 applies silently, Tier 2 confirms before applying, Tier 3 is a PO decision, Tier 4 halts the review. A different axis from Standards Tiers, despite the shared word.
Common mistakes ▸
  • Treating "add standards before running the command" as a hard prerequisite and stalling on a blank template.
  • Reading Actor Identity Shape as background context because it's bundled with four other questions.
  • Assuming Section 9 will catch a bad tech-stack choice later — it structurally can't.
  • Letting composable-vs-fixed-role detection pass unchallenged because it's presented as settled fact.
  • Trying to review Drizzle/DTO code line by line instead of the framing narration and targeted questions.
  • Accepting "no flags" as proof of correctness rather than "nothing the structural checks catch."
  • Typing a bare lock out of habit when a rationale costs one sentence.
  • Reading the Extension Points summary as sufficient instead of applying the Membership Test yourself.
  • Assuming the Locked document stays true of the codebase with no periodic manual check.
Harborview in practice

arch.example.md is a complete, current reference — 788 lines — and worth reading end to end once, not just consulting section by section.

arch.example.md — Section 4.2

varchar actor-label columns, not a uuid foreign key, on every Master table — the concrete outcome of the Actor Identity Shape derivation above, because Harborview has more than one actor kind: authenticated Staff, and System (the dunning scheduler, the Stripe webhook) acting on its own.

arch.example.md — Section 3.1.3

Carried over verbatim from the approved screen-design.md — Portals, Navigation Map, and Screen Inventory (SCR-001–SCR-005) are untouched from Screen Design; only Action Gating and Cross-Cutting UI Rules are generated fresh here, once Section 6's security model exists to generate them from.

arch.example.md — Section 3.2

One real Extension Point, AccountingExportStrategy — the seam for the Xero/QuickBooks export REQ already named as a grounded-but-deferred capability back in Chapter 3. A small, single-point instance of the Core/Extension methodology.

arch.example.md — Section 5

If-Match headers on every mutating endpoint against the version-tracked payers and invoices tables — the concrete wire-level result of the fixed API contract's optimistic-locking rule, cited rather than restated, exactly the pattern api-standards.md itself demonstrates.

arch.example.md — Section 6.5

Logging & Exception Handling as a real, concrete summary — request-correlation IDs, a global exception filter, a business-rule exception type, a real logging and error-tracking tool — rather than the aspirational gap FW-041 found on a real project. This section exists specifically so that gap gets caught here, at generation and review time.

arch.example.md — Verification

Every checkbox annotated with the specific table, section, or column it verified against — the same standard of specificity /review-epics' checks held Chapter 4's epic example to.

Alongside it, technical-standard.example.md and architectural-pattern.example.md are the two files to read for what a hand-authored or generated standards file should actually look like — dense, cited against the fixed contract rather than restating it, and grounded in one real, complete worked path each.
