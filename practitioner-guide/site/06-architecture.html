Stage 6

Architecture

The densest phase in the framework — the last artifact with no code behind it, and the first one every later command treats as literal, binding fact. "Every table name, column, endpoint, auth rule, and enum value becomes law." Get a judgment call wrong here and it costs a schema migration, not a re-write of a document.

Process decision — before the command runs

Pre-authoring standards/ is optional, not required — despite how CLAUDE.md's Workspace Setup reads. Steps 4–7 derive the stack, pattern, and every standards file conversationally. Pre-authoring only earns its keep when you have a hard, non-negotiable mandate you want locked in before the AI proposes something else.

Optional, stack-gated

ascendra-commons module adoption

Applies only when the confirmed backend is NestJS + Drizzle on Postgres or Supabase — full stop, no partial match, no "translate the concept" fallback. Most projects will never see it mentioned. When the gate passes, each of the fifteen modules is evaluated on its own against a real BRD/domain signal — declining a module is as normal an outcome as adopting one.

Every module's public surface is its .core package. Everything past that is an implementation this project's own code never imports directly — the seam that lets a future Model 1 → Model 2 swap happen without touching business logic.The one rule worth remembering
A schema decision disguised as one bullet

Actor Identity Shape

Step 4 derives five things together and asks four explicit questions in the same breath — Actor Identity Shape is the fifth derivation, easy to read past as background. What's actually decided: whether every audit column (who created/updated/deleted a row) is a clickable foreign key, or a plain name string.

A single foreign key can't point at three different kinds of actor — an authenticated Staff member, an unauthenticated tokenized-link customer, and a scheduled job each need their own identity space. Getting this wrong isn't caught by any later check — it's a migration touching every Master table in the schema, project-wide, at once. Stop on this line separately from the four questions below it.

What Section 9 structurally cannot catch

Deviation detection's blind spot

Section 9 flags anything that differs from system-architecture.md — but Step 5's twelve-row tech-stack table is that file the moment you confirm it. If a row is wrong and you approve it anyway, there's nothing to compare it against; the wrong choice and the baseline are the same document.

If you're not sure why a row was recommended, ask "why this and not X" before you confirm, not after.The only real guardrail
A silent fork off BRD wording

Composable capability detection

Section 6.1 scans for phrases like "independently assignable" and, if matched, switches the entire JWT payload shape and every downstream guard — decided once, silently, by pattern-matching, surfacing only as already-settled fact when Concern D frames it. Check it against your own memory of how the client actually described permissions; reversing this after stories are written means rewriting every guard.

Using the review without redoing the AI's work

What's genuinely reviewable vs. what you're meant to trust

The 35 checks run off-screen — you see "no flags," not the work. Give yourself permission to stop trying to parse Drizzle schema blocks and DTO decorators you're not equipped to audit.

SectionGenuinely reviewable?Why
1 — System OverviewYesPlain prose, written for a non-technical stakeholder
4.2 — Table DefinitionsTrustDrizzle/TypeScript code — structurally checked, not written for PO reading
5 — API Contracts / DTOsTrustDecorator blocks — same reason
6.1/6.2 — roles & actionsYesPlain-English sentences, exactly for this purpose
8 — Open DecisionsYesMust be empty before lock — read every row
9 — Deviation DeclarationsYesPlain statements of what differs and why

Spend real attention on the targeted PO question at the end of each concern — the plain-language checkpoints built for exactly this. If "no flags" doesn't sit right, ask which specific check numbers ran and what each found.

The lock confirmation now captures an optional rationale — lock: {what you specifically verified}. Given what locking commits you to, that sentence is worth writing.

Genuinely PO-readable, most POs never find out

Core/Extension methodology

Would every deployment of this base system need this, regardless of which extension is active? If yes → Core. If no → Extension.The Membership Test — two sentences, run it yourself

Concern A's framing gives you a one-sentence summary per extension point — enough to confirm the table exists, not enough to judge whether the seam is drawn right. Open layered-domain-architecture.md yourself and apply the test to the least-obvious seams.

The honest limit

"No undocumented deviations" is enforced by your own review, not a standing structural gate. Locking makes the document binding in principle — it creates no command that continuously checks real running code against it.

  • FW-033 — the standard specified JWKS verification; the code used a shared secret. Caught only when a real login failed.
  • FW-040 — five UI-implementation gaps found only by manually comparing screens against real component source.
  • FW-041 — a documented exception filter and structured logging that existed nowhere in the actual codebase, for months, on a live project.

Spot-check real code against the Locked document periodically — at sprint boundaries is reasonable. There is no command that does this for you.

Terminology recap
  • Actor Identity ShapeFK into one user table, or a self-contained actor-label string — required the moment there's more than one kind of actor.
  • Deviation (Section 9)Only catches drift after the baseline exists — structurally cannot flag a bad choice made in the same confirmation that produces the baseline.
  • Standards Tiers vs. Fix tiersTiers 1–3 classify a generated standards file. Fix tiers 1–4 (shared with /review-epics) classify a review-time correction. Same word, different axis.
Common mistakes ▸
  • Treating "add standards before running the command" as a hard prerequisite and stalling on a blank template.
  • Reading Actor Identity Shape as background context because it's bundled with four other questions.
  • Assuming Section 9 will catch a bad tech-stack choice later — it structurally can't.
  • Letting composable-vs-fixed-role detection pass unchallenged because it's presented as settled fact.
  • Trying to review Drizzle/DTO code line by line instead of the framing narration and targeted questions.
  • Accepting "no flags" as proof of correctness rather than "nothing the structural checks catch."
  • Typing a bare lock out of habit when a rationale costs one sentence.
  • Reading the Extension Points summary as sufficient instead of applying the Membership Test yourself.
  • Assuming the Locked document stays true of the codebase with no periodic manual check.
