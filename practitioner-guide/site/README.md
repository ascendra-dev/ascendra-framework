# Practitioner's Guide Site — Authoring Convention

**There is no build step.** Nothing in this repo parses `practitioner-guide/*.md` into `site/*.html` automatically — no script, no static-site generator, no CI check. Every page here was hand-authored (by an AI session, on request) by reading an existing sibling page for structure and matching it. This document exists so that stays true on purpose instead of by luck: read it before adding a page or updating one after its source `.md` changes.

The `.md` files in `practitioner-guide/` remain the single authored source of truth — every AI-facing cross-reference (`/judgment-check` included) reads them directly, never this site.

**This site is an editorial adaptation, not a literal render.** The `.md` files were written densely, for an AI to parse precisely — that's the right choice for a document `/judgment-check` consumes, but it reads as terse and fragment-heavy to a human (bold-phrase-then-period lists, comma-spliced clauses with the subject dropped). Rewriting the `.md` itself to fix that would risk the precision `/judgment-check` depends on, so instead this site carries the same facts, same structure, same section order, same tables/callouts/case-cards — in independently-written, plainer prose. The two are allowed to diverge in wording; they must never diverge in what they claim is true. When you update one, re-derive the other's content rather than copy-pasting text across — see [`00-orientation.md`](../00-orientation.md) vs. [`00-orientation.html`](00-orientation.html) or [`01-intake.md`](../01-intake.md) vs. [`01-intake.html`](01-intake.html) for a worked before/after.

## When to update this site

- **A chapter's `.md` content changes** → re-read the current `.html` for that chapter, apply the equivalent change **in the site's own plain-language voice**, not by pasting the `.md`'s wording in. Keep everything else in the page identical. Don't regenerate the whole file from scratch — you'll lose hand-tuned structure that has no markdown equivalent (rule-callouts, distgrids, case cards).
- **A new chapter or standalone page is added** → follow the checklist below. Every existing page's sidebar nav and `index.html`'s chapter grid need the same new entry, by hand, in every file.
- **Calibrate density to the chapter, not a fixed formula.** A short, mechanical chapter (Intake) needs little more than fragment-to-sentence fixes. A dense, jargon-heavy chapter (Architecture) earns a genuine worked example added inline the first time an unfamiliar term appears — don't just smooth the grammar of a sentence a newcomer still can't parse.

## The page skeleton

Every chapter page (not `index.html`) is:

```html
<div class="shell">
  <aside class="sidebar">
    <div class="wordmark"><a href="index.html">Practitioner's Guide</a></div>
    <span class="wordmark-sub">Ascendra Framework</span>
    <ul class="navlist"> ... one <li> per page, identical across every file ... </ul>
    <div class="navgroup-label">Case studies</div>
    <ul class="navlist">...</ul>
  </aside>
  <main>
    <div class="readcol">
      <div class="chapter-eyebrow">...</div>
      <h1 class="title">...</h1>
      <p class="dek">...</p>
      <div class="chapter-links">...</div>
      <nav class="jumpnav">...</nav>
      <section class="block" id="...">...</section>
      <!-- repeat per section -->
      <footer class="pagefoot">Renders <code>practitioner-guide/{file}.md</code>...</footer>
    </div>
  </main>
</div>
```

Copy this shell from the nearest existing sibling page, not from memory — the sidebar `<ul class="navlist">` must be byte-identical (apart from which `<li>` carries `class="active"`) across every single page. A page that drifts from this breaks nothing visibly but makes the next edit harder to trust.

## CSS class vocabulary (`assets/site.css`)

Never invent ad hoc inline styles or a one-off class for something an existing class already does. Reuse from this list first; only add a new class when the content shape genuinely doesn't exist yet (that's how `.stagegrid`/`.stagecard`/`.domain-badge`/`.regionband`/`.anchor-note` were added for `lifecycle-map.html` — a stage-by-stage map needed a shape none of the prose chapters had).

| Class | Use for |
|---|---|
| `.chapter-eyebrow`, `.title`, `.dek`, `.chapter-links` | Page header block — eyebrow label, H1, one-sentence dek, the "generated by these commands" line |
| `.jumpnav` | Sticky-free pill nav to in-page anchors |
| `section.block`, `.block-label`, `h2.block-title`, `h3.sub-title` | The standard content section wrapper and its labeled header |
| `.prose` | Plain paragraphs/lists at reading width |
| `.rule-callout` | A single quotable decision test, pulled out in serif italics |
| `.caution` | "What breaks downstream" boxes |
| `.tblwrap` / `table.dtable` | Any tabular data (renders markdown tables) |
| `.distgrid` / `.distcard` | Side-by-side short comparison cards (2–3 items) |
| `.gb-wrap` / `.gb-card.good` / `.gb-card.bad` | Good vs. bad worked-example comparison |
| `details.mistakes` | Collapsible "Common mistakes" list |
| `.casecard` | Pointer into a real example file (e.g. Harborview) |
| `.recaplist` / `.reflist` | Terminology recap chips / linked reference list |
| `.stagegrid` / `.stagecard` / `.domain-badge` / `.regionband` / `.anchor-note` | Stage-map cards grouped by domain region — introduced for `lifecycle-map.html`, reuse for any future stage-by-stage overview page |

If you add a new class, add it to this table in the same change.

## Relative path rules

`site/` sits **two** directories below the repo root (`ascendra-framework/practitioner-guide/site/`). Get this wrong and links look right in a code review but 404 in a browser — it happened once already (`.claude/commands/*.md` links shipped as `../.claude/...` instead of `../../.claude/...`).

| From | To | Path |
|---|---|---|
| Any `site/*.html` | Another `site/*.html` (sibling) | `other-page.html` |
| Any `site/*.html` | Repo-root file (`PROJECT-LIFECYCLE.md`, `SDLC.md`, `.claude/commands/*.md`, `decisions/*.md`) | `../../whatever` |
| `site/case-studies/*.html` | A sibling `site/*.html` | `../other-page.html` |
| `site/case-studies/*.html` | Repo-root file | `../../../whatever` |

## Before calling a change done: verify links

There's no checked-in tool for this — run it ad hoc from `practitioner-guide/site/`:

```bash
python3 -c "
import re, os
files = [f for f in os.listdir('.') if f.endswith('.html')] + ['case-studies/'+f for f in os.listdir('case-studies') if f.endswith('.html')]
bad = []
for f in files:
    base = os.path.dirname(f)
    content = open(f).read()
    for m in re.finditer(r'href=\"([^\"#][^\"]*)\"', content):
        href = m.group(1)
        if href.startswith('http'): continue
        path = os.path.normpath(os.path.join(base, href))
        if not os.path.exists(path):
            bad.append((f, href))
for f,h in bad: print('MISSING', f, '->', h)
print('All internal links resolve.' if not bad else f'{len(bad)} broken link(s).')
"
```

## Adding a new page — checklist

1. Write the page using the skeleton and class vocabulary above.
2. Add its `<li>` to the `navlist` in **every** other chapter's sidebar, plus `case-studies/harder-cases.html` (with the extra `../`), at the correct relative path depth.
3. Add a `.chaptercard` to `index.html`'s `.chaptergrid`.
4. Cross-link it from `00-orientation.md` **and** `00-orientation.html`'s "Where to find more" if it's foundational reading (keep both in sync — the `.md` is the source, the `.html` mirrors it).
5. Run the link-check snippet above.
6. If you introduced new CSS classes, add them to the vocabulary table above.
