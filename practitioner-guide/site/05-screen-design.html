Mocks and real implementation each guessed independently, so a PO-approved mock carried no actual weight over what got built. Screen Design closes that gap: the mock you approve here is the same mock implementation is later held to. What Screen Design is, and why it exists as its own stage

What is Screen Design? It's the stage that decides, for every screen a user will see, exactly what shape it takes — its Surface (a routed Page, or an overlay Dialog, Sheet, or Drawer) and its UI Pattern (Form, Dashboard, Report, Table-List, or Detail). Each one is cited to a real, checkable entry in ascendra-ui's component catalog, never invented.

Why does this get its own stage, before architecture even starts? Three compounding problems led here. /implement-story never read the architecture section that was supposed to define screen shape — confirmed by grep, zero references. That section had no field for screen shape in the first place: its columns recorded portal, route, and purpose, but nothing about whether a screen was a page, a dialog, a sheet, or a drawer. And the API and data model were being designed against screen needs inferred a second time, generically, from BRD requirements — disconnected from what a screen actually renders. Screen Design exists to close all three gaps at once.

Where does a screen's shape come from? Entirely from the BRD's own journeys and requirements, matched against ascendra-ui's real catalog — there's no architecture dependency yet. That's why this stage can run for every approved epic at once, before any technology decision is made.

The test you can actually run

Verifying a catalog citation without ascendra-ui knowledge

Every Screen Inventory row's Matched Reference is supposed to name a real row in ascendra-ui's component catalog, or — for Report/Table-List, which have no composite example — a primitive composition. Whether "Customer Profile" or "Create Product Listing (multi-section, mixed grid)" is a real catalog entry, rather than something invented to sound plausible, isn't something you can check yourself against a 1,500-line reference doc.

The test you can actually run: open the mock, not just the table. /review-screen-design already tells you to do this — "open the base mocks now alongside this table, do the navigation and screen shapes match what you'd expect a user to see?" You don't need to know what the catalog says a pattern looks like. You need to know whether the rendered HTML looks like something a Finance Manager would actually be shown. That's a judgment any PO can make — the same skill you already use reviewing a live product, just applied to a static file.

When a screen's shape looks unfamiliar anyway: ask the AI to name the exact catalog row it matched — not "what pattern did you use," which invites a restated category label, but "show me the row in the reference doc this came from." A vague answer like "a standard form pattern," with no row to point to, is the failure mode this whole phase exists to prevent, restated instead of caught.

The closest: prefix — undocumented, worth knowing anyway

Harborview's own Screen Inventory has two rows prefixed closest:. Neither the template's guidance nor its worked example ever defines this convention formally — it's something the canonical example uses without being told to. It means the AI found no exact catalog match and cited the nearest real one instead, which is different from an invented shape: closest: still points at something real, just not a precise fit.

Legitimate

The screen shape is genuinely novel — nothing in the catalog resembles it. A first-of-its-kind screen has nowhere better to point. Note it and move on.

Not legitimate

The AI stopped at the first plausible-ish row instead of checking primitive compositions or the showcase reference. Push back and ask it to look again.

Because this isn't a formally defined convention, treat every closest: you see as worth a one-line reason from the AI — even though no check currently forces one. It's the cheapest way to catch the second case before it ships as an approved mock.

Decision heuristic

Portal boundaries: when two personas share one, and when they don't

The base rule is simple: two personas share a portal if they log into the same app and their navigation differs only by which items are visible. Different visibility, same shell — one portal.

Two personas sharing the same nav shell but entering via genuinely different auth flows are two portals, even if the nav items are otherwise identical.The sharper addition

Nav-item overlap doesn't settle the question — the login mechanism does. Two personas can share 90% of the same nav and still need separate portals if one enters via SSO through the client's identity provider, another via a magic link, and a third via an ordinary standing session. A shared portal implies one session model underneath it, not just one visual shell.

Harborview's single shared portal — Finance Manager and Account Owner, both on a standing session, both entering the same way — is the simple baseline, not the hard case. There's no auth-flow split to force a division, which is exactly why it's a clean teaching example rather than a stress test of the rule. See Harder Cases for a real worked instance where it does bite: a School Admin and Bursar sharing one SSO-backed portal, while Parent — a completely separate magic-link flow — needs its own.

What Architecture can and can't change

Sections 1–3 — structurally locked

Portals, Nav Map, Screen Inventory. Architecture carries these into 3.1.3.1–3.1.3.3 as-is, never re-derived. Approving Screen Design is the final word here.

Section 4 — a forecast, not a lock

Per-Screen Data Requirements only "feed" architecture's data modeling — a deliberately weaker verb. A different real data shape emerging is a normal refinement, not a regression, and it does not require /assess-change.

Architecture does real modeling work — normalizing entities, resolving relationships, deciding what's a foreign key versus a join table — and it's completely normal for that to surface a shape Section 4 didn't predict. Don't let it feel like your approval is being violated; it isn't. What would require /assess-change is a change to Sections 1–3 after approval: a new screen, a portal split, a different Surface — because those are the parts you actually locked.

Why base and patch are separate

The two-pass mock

/gen-ui-mocks runs twice against the same files, in two different modes, invoked by two different upstream commands — never run standalone by the PO. This follows directly from what each pass actually needs to exist first, not from an arbitrary process boundary.

Base mode

Invoked by /gen-screen-design. Full layout, navigation, real component fidelity. No gating captions or cross-cutting banners yet — Action Gating and Cross-Cutting UI Rules both depend on architecture Section 6, which genuinely doesn't exist at this point.

Patch mode

Invoked by /gen-architecture once Section 6 exists. Additive only — gating captions and cross-cutting banners, never touching reviewed layout. Reviewed inside /review-architecture Concern A, not as its own gate.

Base mode has to run and be approved before Architecture starts for the same reason Section 4's Data Requirements exist at all: architecture's Data Model and API Contracts work needs real, PO-reviewed screen data to design against, rather than inferring it a second time from BRD requirements alone, disconnected from what a screen actually renders. The mock is what makes those data needs concrete enough to review before they become an API surface.

A real strength, not a caveat: both passes read the same living registry of corrections to ascendra-ui's own docs that /implement-story has always consulted — covering cases where the documented component doesn't match the real source. One real example: the docs describe a showCloseButton prop on a dialog component that doesn't actually exist, a genuine TypeScript build error if used. Before this was fixed, a mock could be built from a documented-but-fictional pattern, get approved here, and then not match what implementation correctly built — silently defeating the reason this phase exists. Now the mock you approve is built from the same corrected source implementation is held to.

Full depth

Portal, Screen, Surface, UI Pattern

Portal

A navigation shell — one app, one session model. Harborview has one (Staff App).

Screen

One Screen Inventory row. Equal weight regardless of Surface — an overlay Dialog is exactly as much "a screen" as a routed Page.

Surface

The container: Page, Dialog, Sheet, or Drawer. How the screen is presented.

UI Pattern

The internal content shape: Form, Dashboard, Report, Table-List, Detail. Independent of Surface — a Form can live on a Page (Harborview's SCR-004) or inside a Sheet (SCR-002).

If you're counting how many screens a project has, count Screen Inventory rows, not routes: Harborview has five screens (SCR-001 through SCR-005), not three pages plus two afterthoughts. Knowing a screen's UI Pattern tells you nothing about its Surface, and vice versa — that's exactly why both fields are mandatory on every row.

A criterion to apply carefully

The template's criterion for proposing Tabs is specific: only when the source journey or requirement describes 2+ independent sub-views reachable from one entry point with no route change — and even then, Tabs is layered onto whatever Surface/Pattern was already chosen, never a default on its own. Harborview's example doesn't demonstrate real Tabs usage at all — no row uses them, and its own verification checklist says so directly. When you hit a real case, apply the criterion straight to your own journey text — you can't pattern-match from the canonical example here, because it never had to make this call.

Terminology recap
  • Every Section 3 row is "a Screen" with equal weightRegardless of Surface — a Dialog carries the same status as a routed Page.
  • The closest: prefixAn approximate match, not an exact one — worth a one-line reason, even though no check currently forces it.
Common mistakes ▸
  • Reviewing only the Screen Inventory table and never opening the generated mock.
  • Accepting a vague match answer instead of insisting on the specific catalog row.
  • Waving through a closest: citation without asking why no exact match exists.
  • Treating "same nav items" as sufficient to merge two personas into one portal, without checking auth flow.
  • Panicking when Architecture's real data model doesn't match Section 4's forecast.
  • Treating a Dialog or Sheet as a lesser "sub-screen" instead of a full Screen Inventory row.
  • Proposing Tabs because a screen "feels like" it should have them.
  • Forgetting base-mode mocks intentionally have no gating captions yet.
Harborview in practice

screen-design.example.md is the worked model for this whole chapter — one portal, five screens, deliberately the easy case.

SCR-001, SCR-003 — Page, Table-List

Both cleanly matched to a primitive composition ("Data Table + Empty State," "Data Table + Page Bar"), since Table-List has no composite example in the catalog — exactly per the rule above.

SCR-002 — Sheet, Form, closest: Customer Profile

The clearest closest: example in the wild: an overlay Form for creating or editing a Payer, matched to the nearest real pattern rather than an exact one. Use this row to practice the "why no exact match" question on a real instance.

SCR-004 — Page, Form (Complex), closest: Create Product Listing

The same closest: pattern on a routed Page rather than an overlay, showing the prefix isn't tied to any one Surface.

SCR-005 — Page, Detail, Item + Card

An invoice detail screen citing a primitive pair rather than a named composite — and the one row whose Notes column shows a journey citation spanning two separate BRD journeys (4.1 and 4.2) for the same screen.

The document's own header note is worth reading directly: journey citations here reference a specific numbered step within a BRD journey (e.g. "Journey 4.1, step 1"), never an invented sub-heading like "4.1.1" — BRD journeys number their steps as a plain list, not as sub-headings, and this document only ever cites what's really there.
