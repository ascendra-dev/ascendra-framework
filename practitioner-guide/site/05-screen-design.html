What Screen Design is, and why it exists as its own stage

What is Screen Design? It's the stage that decides, for every screen a user will see, exactly what shape it takes — its Surface (a routed Page, or an overlay Dialog, Sheet, or Drawer) and its UI Pattern (Form, Dashboard, Report, Table-List, or Detail) — each cited to a real, checkable entry in ascendra-ui's component catalog, never invented.

Why does this get its own stage, before architecture even starts? Before this phase existed, implementation and mocks each independently guessed what a screen looked like. That's not a guess — a grep found /implement-story never once actually read the architecture section that was supposed to define screen shape. A PO-approved mock carried no real weight over what got built. This stage closes that gap: the mock you approve here is the same mock /implement-story is later held to.

Where does a screen's shape come from? Entirely from the BRD's own journeys and requirements, matched against ascendra-ui's real catalog — there's no architecture dependency yet. That's why this stage can run for every approved epic at once, before any technology decision is made.

The test you can actually run

Verifying a catalog citation without ascendra-ui knowledge

You can't independently verify a Matched Reference is a real catalog row in a 1,500-line reference doc. Open the mock, not just the table — you don't need to know what the catalog says a pattern looks like; you need to know whether the rendered HTML looks like something a Finance Manager would actually be shown. That's a judgment any PO can make.

The closest: prefix — undocumented, worth knowing anyway

Not a formally recognized convention — the canonical example uses it without ever being told to. It means the AI found no exact match and cited the nearest real one instead.

Legitimate

The screen shape is genuinely novel — nothing in the catalog resembles it. Note it and move on.

Not legitimate

The AI stopped at the first plausible-ish row instead of checking primitive compositions or showcase-reference.md. Push back.

Decision heuristic

Portal boundaries: when two personas share one, and when they don't

Two personas sharing the same nav shell but entering via genuinely different auth flows are two portals, even if the nav items are otherwise identical.The sharper addition

Harborview's single shared portal (Finance Manager + Account Owner, both standing session) is the simple baseline, not the hard case — there's no auth-flow split to force a division. See Harder Cases for the multi-portal RBAC scenario Harborview doesn't exercise.

What Architecture can and can't change

Sections 1–3 — structurally locked

Portals, Nav Map, Screen Inventory. Architecture carries these into 3.1.3.1–3.1.3.3 as-is, never re-derived. Approving Screen Design is the final word here.

Section 4 — a forecast, not a lock

Per-Screen Data Requirements only "feed" architecture's data modeling. A different real data shape emerging is a normal refinement, not a regression — it does not require /assess-change.

Why base and patch are separate

The two-pass mock

Base mode

Invoked by /gen-screen-design. Full layout, navigation, real component fidelity. No gating captions yet — Section 6 (security) doesn't exist at this point, so there's nothing to gate against.

Patch mode

Invoked by /gen-architecture once Section 6 exists. Additive only — gating captions and cross-cutting banners, never touching reviewed layout.

A real strength: both passes read hard-instructions.md — the same corrections registry /implement-story consults. Before this, a mock could be built from a documented-but-fictional pattern, get approved, and not match what implementation correctly built — silently defeating the reason this phase exists.

Full depth

Portal, Screen, Surface, UI Pattern

Portal

A navigation shell — one app, one session model.

Screen

One Screen Inventory row. Equal weight regardless of Surface — an overlay Dialog is exactly as much "a screen" as a routed Page.

Surface

The container: Page, Dialog, Sheet, or Drawer. How the screen is presented.

UI Pattern

The internal content shape: Form, Dashboard, Report, Table-List, Detail. Independent of Surface — a Form can live on a Page or inside a Sheet.

If you're counting how many screens a project has, count Screen Inventory rows, not routes.

A criterion to apply carefully

Harborview's example doesn't demonstrate real Tabs usage at all — no row uses them. When you hit a real case, apply the template's criterion directly to your own journey text (2+ independent sub-views, one entry point, no route change) — you can't pattern-match from the canonical example here.

Terminology recap
  • Every Section 3 row is "a Screen" with equal weightRegardless of Surface — a Dialog carries the same status as a routed Page.
  • The closest: prefixAn approximate match, not an exact one — worth a one-line reason, even though no check currently forces it.
Common mistakes ▸
  • Reviewing only the Screen Inventory table and never opening the generated mock.
  • Accepting a vague match answer instead of insisting on the specific catalog row.
  • Waving through a closest: citation without asking why no exact match exists.
  • Treating "same nav items" as sufficient to merge two personas into one portal, without checking auth flow.
  • Panicking when Architecture's real data model doesn't match Section 4's forecast.
  • Treating a Dialog or Sheet as a lesser "sub-screen" instead of a full Screen Inventory row.
  • Proposing Tabs because a screen "feels like" it should have them.
  • Forgetting base-mode mocks intentionally have no gating captions yet.
