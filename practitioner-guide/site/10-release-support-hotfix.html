Release, Support & Hotfix

Three things that look like they could be one "ship it and watch it" step. Get the hotfix git logic wrong and the fix you deployed can vanish from main without anyone touching it on purpose — the single most consequential thing in this chapter to get right.

Sprint Closure & Release

Where this sprint's learnings get checked against not-yet-built scope, and a client-facing version boundary is decided — one that doesn't always line up with a sprint boundary.

Support

A standing posture, not an event. Runs once per project, ends one of two structurally different ways.

Hotfix Cycle

An emergency deviation — no sprint planning, no UAT — for the moment when waiting for the normal pipeline is the wrong call.

Forward-looking learnings, vs. sprint-specific noise

/gen-stories generates a wave from the Locked architecture and Approved BRD as they stand at that moment — it never re-reads a prior sprint's retrospective. Step 8 is the one deliberate place that catches staleness before the next wave builds on it, and it hands you /assess-change as the fix.

Not by sprint

Release notes are versioned by release

A sprint ships as its own release

UAT passes, the client wants it live immediately. One sprint, one version, one deploy — the common case.

Two sprints batch into one release

A client's monthly change-window policy means both land in the same deploy. Treat the deploy, not the sprint boundary, as the trigger — one version, not two back to back.

/gen-release-notes reads exactly one sprint plan file. If batching, it won't fold the earlier sprint in for you — point it at the later sprint and manually merge, or read both files in the same session first.

Git process, explained clearly

The Hotfix Cycle

Trunk-based: one branch per story, cut from main, merged directly back. There is no persistent sprint-integration branch. A hotfix branch is cut from main like any story branch, fixed, verified, PR'd, and merged — the moment it merges, every story branch created after that point already contains it. Nothing to do for those.

The one thing that needs a manual check

A story branch cut before the hotfix merged has a frozen copy of main with no knowledge the fix happened. If it touches the same lines and merges without pulling main in first, its version silently wins — overwriting the hotfix. Rule of thumb: the instant a hotfix PR merges, pull main into every story branch that was already open at that moment, before its own PR is allowed to merge.

A production defect is automatically escalated one severity level. Log a batched defect in the Support Log with a target sprint — it doesn't automatically show up in a future sprint's story list the way a UAT carry-forward story does.

Terminology recap
  • Hotfix branchCut from main like any story branch. No persistent sprint-integration branch exists to merge into.
  • Support LogThe running defect log for the monitoring period — where a batched production defect is tracked so it doesn't disappear.
Common mistakes ▸
  • Treating the retrospective as if it already corrects stale scope — Step 8 and /assess-change are the actual path.
  • Assuming one release note per sprint is the default.
  • Running /gen-release-notes once and assuming it picked up an earlier batched sprint too.
  • Looking for a sprint-integration branch that doesn't exist in this framework's git model.
  • Assuming a hotfix "reaching" the codebase is the risk — it already has, the moment its PR merges. The risk is an older, already-open branch overwriting it.
  • Not escalating a defect's severity when found in production.
  • Leaving a project's brief Status at Active after the support window closes cleanly.
