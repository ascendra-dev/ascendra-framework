Stage 11–12

Release, Support & Hotfix

Three things that look like they could be one "ship it and watch it" step — the framework deliberately keeps them apart, because each does a job the other two can't. Sprint Closure checks this sprint's learnings against not-yet-built scope. Support is a standing posture, not an event. The Hotfix Cycle is a deliberate emergency deviation — no sprint planning, no UAT — for the moment when waiting for the normal pipeline is the wrong call. Get the hotfix git logic wrong and the fix you deployed can vanish from main without anyone touching it on purpose — the single most consequential thing in this chapter to get right. If that sounds alarming, good — keep reading, because the mechanism is simple once you see it, and this chapter starts from zero.

Sprint Closure & Release

Where this sprint's learnings get checked against not-yet-built scope, and a client-facing version boundary is decided — one that doesn't always line up with a sprint boundary.

Support

A standing posture, not an event. Runs once per project, ends one of two structurally different ways.

Hotfix Cycle

An emergency deviation — no sprint planning, no UAT — for the moment when waiting for the normal pipeline is the wrong call.

/close-sprint Step 8

Forward-looking learnings, vs. sprint-specific noise

/gen-stories generates a wave from the Locked architecture and Approved BRD as they stand at that moment — it never re-reads a prior sprint's retrospective. Step 8 is the one deliberate place that catches staleness before the next wave builds on it, and it hands you /assess-change as the fix. Step 6's retrospective, by contrast, only logs process notes — it corrects nothing on its own.

SignalFlag it, or noise?
Client clarifies a business rule mid-UAT that a later epic's logic depends on (e.g. a rounding rule that a future interest calculation also needs)Flag — the not-yet-built epic inherits the wrong assumption if nobody tells it
A defect in this sprint's own stories, already fixed on the story branch before mergeNoise — already resolved, nothing to propagate
A UI preference about this sprint's screens (button copy, column order)Noise — sprint-local, handled through normal PR review
UAT reveals a domain concept discovery never modeled (a new actor type, a relationship pattern) that a future epic will needFlag — the same "structurally new axis" test from Chapter 3, one stage later
A carry-forward story moving to next sprint purely for capacity reasons, no new informationNoise — ordinary capacity management, already handled in Step 7
Does this new information change what a not-yet-built epic should have been told, or does it only affect work already built or already has its own fix in hand?The test that separates the two

/close-sprint will not run /assess-change for you — Step 8 explicitly waits for the PO to either run it or say to proceed without it. Don't let "I'll deal with it later" become the default answer; the whole point of asking before the next wave, not after, is that /gen-stories for that wave hasn't run yet, so the correction is still cheap.

Not by sprint

Release notes are versioned by release

The output path is keyed by version string, not sprint number — the template says why directly: "since a release doesn't always map 1:1 to a sprint." Every time a sprint closes, there are really two decisions to make: is this the moment a release goes out, or does this sprint's work bundle with a later one — and if a release is going out now, what version number does it get?

A sprint ships as its own release

UAT passes, the client wants it live immediately. One sprint, one version, one deploy — the common case.

Two sprints batch into one release

A client's monthly change-window policy means both land in the same deploy. Treat the deploy, not the sprint boundary, as the trigger — one version, not two back to back.

/gen-release-notes reads exactly one sprint plan file. If batching, it won't fold the earlier sprint in for you — point it at the later sprint and manually merge the earlier sprint's stories into the What's New and Change Summary sections yourself, or read both files in the same session first.

The version number itself is an ordinary semver call, not a framework-prescribed scheme: a first production release is 1.0.0; a deploy that only adds capability bumps the minor number; a hotfix-only deploy bumps the patch number. The number belongs to the deploy event, not to whichever sprint number happens to be freshest.

Git process, explained clearly

The Hotfix Cycle

Trunk-based: one branch per story, cut from main, merged directly back. There is no persistent sprint-integration branch. This section was rewritten in the framework's own files because the old wording described a git object — "the current sprint's working branch" — that doesn't exist anywhere in this git model. Once you hold that fact fixed, the logic is genuinely simple, but only if you walk it through step by step.

  1. A Critical or High defect is confirmed in production; the PO confirms a hotfix should proceed.
  2. A hotfix branch is cut from main — hotfix/{PROJECT_CODE}-{issue-description} — the same starting point every story branch uses.
  3. The fix is implemented and verified on that branch, scoped strictly to the defect's own acceptance criteria.
  4. A PR is raised against main. The PO reviews and approves it — the same gate as any other PR.
  5. The PR merges into main. This is the moment the fix becomes part of the trunk.
  6. The PO approves production deployment, rollback plan in hand; smoke tests confirm it's healthy.
  7. Because every story branch is cut from main and merges back into main — there's no separate branch to "merge the hotfix into" — every story branch cut after step 5 already contains the fix automatically. Nothing to do for those.
The one thing that needs a manual check

A story branch cut before the hotfix merged has a frozen copy of main with no knowledge the fix happened. If it touches the same lines and merges without pulling main in first, git has no way to know the hotfix's version should win — its version silently wins instead, overwriting the fix. Rule of thumb: the instant a hotfix PR merges, pull main into every story branch that was already open at that moment, before its own PR is allowed to merge — don't wait to discover which files actually collided.

A worked timeline. Harborview is mid-Sprint 02 when a Critical defect surfaces in production: an invoice's VAT total is calculated wrong for a rounding edge case. Two Sprint 02 story branches are already open — story/US-01-011 (cut from main Monday) and story/US-01-014 (not yet started). The hotfix branch is cut Tuesday morning, fixed, reviewed, and merged into main Tuesday afternoon.

story/US-01-014 gets cut Wednesday, after the merge — it already includes the VAT fix, nothing to do. story/US-01-011 was cut Monday, before the merge — even though its own work has nothing to do with VAT calculation, skipping the pull-main step means whatever that branch currently has for the VAT logic (the pre-fix version, frozen from Monday) is what lands once its PR merges, silently undoing Tuesday's hotfix. It isn't about the hotfix "not reaching" the rest of the codebase — main already has it the moment the PR merges. It's about one specific class of branch, already open and forked before the fix landed, being able to overwrite it on its own way in.

What triggers a hotfix vs. what gets batched

SeveritySLAIn production
CriticalFix within 4 hoursHotfix immediately, no exceptions
HighFix within 1 business dayHotfix immediately
MediumFix within current sprintBatched into a future sprint
LowNext sprint or backlogBatched

A production defect is automatically escalated one severity level — a bug that would have been Medium in UAT can be High once live. Check the escalated severity, not the pre-release one, before deciding whether it's a hotfix.

What "batched" actually means: a Medium/Low production defect isn't dropped just because it isn't urgent. Log it in the Support Log with a target sprint, the same discipline the Deferred Defect Process requires during UAT. It doesn't automatically show up in a future sprint's story list the way a UAT carry-forward story does, because it was never a story in the first place — when that target sprint is planned, the PO is responsible for pulling it in explicitly, typically through /assess-change if it needs real implementation work.

Support's two end states

Stage 12 is entered once per project, after the final sprint's deployment, and runs for a monitoring window (default 30 days). The practical trigger for choosing between its two end states: is there a firm end date with no further paid engagement, or is the relationship ongoing?

ClosureRetainer
TriggerScope delivered, window elapses clean, no further agreementClient wants ongoing work, new agreement in place
What changesBrief Status → CompleteNew/addendum brief; project stays Active
What gets producedA formal closure document — what was delivered, open known issues, handover notesNo closure document; the normal stage cycle applies to whatever the retainer covers

The decision isn't really a framework mechanic — it's a business-relationship fact you already know by the end of the monitoring window. A project that's functionally done but never gets its brief status set to Complete looks, to anyone reading the project registry later, like a project still in delivery.

Terminology recap
  • Forward-looking learningInformation from this sprint that would change what a not-yet-built epic should have been told. Distinct from the retrospective, which corrects nothing on its own.
  • Release version vs. sprint numberA release is keyed by v{version}, decided when a deploy actually happens. A sprint closing doesn't by itself trigger one.
  • Hotfix branchCut from main like any story branch. No persistent sprint-integration branch exists to merge into.
  • Support LogThe running defect log for the monitoring period — where a batched production defect is tracked so it doesn't disappear.
  • Closure vs. RetainerThe two end states of Stage 12, distinguished by whether paid engagement continues, not by any technical condition.
Common mistakes ▸
  • Treating the retrospective as if it already corrects stale scope — Step 8 and /assess-change are the actual path.
  • Letting a real forward-looking learning slide because "we'll catch it when we get to that epic" — nothing else re-checks it.
  • Flagging ordinary sprint-specific feedback as a Step 8 item, adding noise to a check meant for genuine scope corrections.
  • Assuming one release note per sprint is the default.
  • Running /gen-release-notes once and assuming it picked up an earlier batched sprint too.
  • Looking for a sprint-integration branch that doesn't exist in this framework's git model.
  • Assuming a hotfix "reaching" the codebase is the risk — it already has, the moment its PR merges. The risk is an older, already-open branch overwriting it.
  • Not escalating a defect's severity when found in production.
  • Logging a batched production defect nowhere durable, letting it silently vanish before its target sprint.
  • Leaving a project's brief Status at Active after the support window closes cleanly.
Harborview in practice
release-notes.example.md — Section 1 (What's New)

Groups by feature area, no story IDs, no table names, no API routes anywhere in the client-facing sections — the discipline this chapter's release-notes guidance is built around.

Section 4 (Known Limitations)

Names what didn't ship — dunning reminders, payment collection — as real limitations with a planned epic, rather than silently omitting them.

Section 5 (Deployment Notes)

A real, populated environment variable change (INVOICE_NUMBER_PREFIX) with an explicit required action — the level of specificity to hold every Deployment Notes section to, hotfix or ordinary release alike.

Section 6 (Change Summary)

Honestly records "Epics completed: 0 (EPIC-002 and EPIC-003 partially delivered)" rather than rounding up — the same "don't invent, don't round up" discipline that matters even more once a release starts batching multiple sprints' partial delivery together.
