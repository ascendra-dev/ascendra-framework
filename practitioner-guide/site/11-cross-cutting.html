Cross-Cutting Commands

Nothing puts /assess-change, /update-status, or /project-status in front of you the way a staged command is. You have to remember to reach for them yourself — usually at the exact moment reaching for the right tool matters most.

The Promotion Gate surprise

If the change is already sitting in the BRD's Parking Lot, /assess-change stops mid-session to redirect you to a discovery pass first — right behavior, but a wasted read-and-classify cycle if it surprises you. The habit that avoids it: glance at Section 15 yourself before describing the change.

The two-invocation habit

A single invocation never both finds and resolves. Analysis Mode surfaces findings and logs them Open; Resolve Mode walks you through them. Stop after the first and move to /review-X, and those findings sit Open forever — logged, never weighed. When anchor drives it, both passes happen automatically; running standalone, you're the one who has to remember the second invocation.

Common mistakes ▸
  • Defaulting to Pattern 2 because it's cheaper, without pointing to the actual BRD sentence.
  • Describing a change without first checking whether it's already a Parking Lot entry.
  • Assuming a /review-X command advances every status field, when it only sets the one it exists to grant.
  • Treating a GitHub PR merge as the story-file status update — they're two separate actions.
  • Inventing a remedy command for sprint slip risk because the dashboard's generic line implies one exists.
  • Running /judgment-check once and moving straight to /review-X without a second invocation to resolve findings.
  • Treating "no findings" as a quality certification rather than "nothing checkable stood out."
How these four work together

/project-status is where a real Tuesday starts — you run it, work down the ATTENTION list, and most items resolve into either /update-status (a stale field) or /assess-change (a real scope change). /judgment-check sits at a different point in the same discipline — not a Tuesday habit, a pre-gate one: it runs against whatever's about to go through /review-X, gets resolved, and only then does the walkthrough proceed.
