Stage 9–10

Testing, QA & UAT

Two separate gates, not one step with two names. Stage 9 (QA) asks a technical question: does the merged code do what the stories said it would? Stage 10 (UAT) asks a different question entirely: does the running system, operated by the PO's own hands, actually deliver the business outcome the BRD promised? A sprint can clear QA cleanly — full suite green, zero open Critical/High, coverage met — and still fail UAT, because a feature can be technically correct against its acceptance criteria and still be missing an obvious step, or contradict what the client actually meant. Collapsing the two into one step means skipping one confirmation or the other. If that distinction feels academic right now, keep reading — this chapter starts from zero.

Where a UAT checklist actually comes from

What generates it? /gen-uat-checklist reads every story file for the sprint and turns each acceptance criterion into one test case — real steps, an observable expected result. It runs once all sprint stories are Merged, after Stage 9's QA confirmation is recorded.

Why two separate gates instead of one? QA and UAT check genuinely different things, and they can genuinely disagree. Every test can pass — the code does exactly what the stories said — while UAT still fails, because what the stories said wasn't actually what the client needed. Collapsing the two into one step means either skipping the technical confirmation (UAT starts on code nobody has confirmed is stable) or skipping the business confirmation (a sprint ships on automated passes alone, with no one but the AI ever having operated the actual feature). Passing one gate is never evidence you'll pass the other.

Two automatic escalations easy to under-apply: a defect found in production escalates one level; any security or cross-tenant data defect is always Critical, no proportionality exception — don't classify a cross-tenant leak as Medium because only one field was exposed.

The Deferred Defect Process

The current, corrected rule

A defect can be set to Deferred only when all four conditions hold:

  • 1. SeverityMedium or Low, or High with the explicit agreement condition 3 requires. Critical can never be deferred, under any condition.
  • 2. Client informedIf the project has an external client, they've been told about the defect and its deferral.
  • 3. PO approval, individually recordedFor a High defect specifically, explicit and recorded against that one defect's own entry — not covered by a blanket sprint sign-off.
  • 4. Target sprint agreedA specific sprint for the fix, recorded in the defect log.
A High defect does not get deferred by the PO signing the overall sign-off line at the bottom, or by approving the sprint as a whole with the defect merely listed somewhere in it. The QA sign-off checklist's own exception line is explicit: a High defect can be overridden to Deferred only by explicit PO decision, recorded in the Defects table with who made the call and when.Read condition 3 literally
✓ Correctly deferred — DEF-14, High
CSV export fails, but the on-screen data is fully usable, the Finance Manager confirmed export isn't needed until month-end (3 weeks out), and the PO recorded the decision against this specific defect with a target sprint.

All four conditions met, individually, for this one defect.

✗ Should not be deferred — DEF-15, High
Void Invoice silently fails for >10 line items — no error shown, no way for the user to know it didn't work.

No real workaround exists (the user can't even detect the failure). A silent, undetectable failure on a money-moving action should fail the PO's honest risk-weighing.

The difference between the two isn't the severity label — both are High. It's whether a real workaround exists and whether the PO can honestly say, in writing, why shipping without the fix is safe for the time between now and the target sprint. If you can't write that sentence honestly, don't defer it — fix it now.

Process decision

When the full test execution report is warranted

Stage 9's own guidance says the fuller report is for a "formal, client-facing QA record," but neither the command nor the template states a crisp trigger — the one real gap the framework's own audit found in an otherwise well-explained relationship.

Is there an external stakeholder who expects to be shown quality evidence, not just told it happened? Is there a compliance or contractual reason a formal record has to exist? If no to both, a one-line sprint-plan note is sufficient.The trigger test

If either answer is yes, produce the full report — it's the gate artifact UAT actually reads in that case, giving a client or auditor the aggregated pass rate, defects, and blocked items instead of story-level files to reconcile themselves. Producing a six-section formal report nobody on the client side will ever open is ceremony, not QA — it costs real PO time synthesizing a document, and that time comes from somewhere.

Skipping the full report doesn't mean a lighter bar — the suite still has to pass, Critical/High still has to be zero (or deferred), coverage still has to clear the threshold, before that one line gets written.

Density guidance

Turning an AC into something a client can run

Written for engineers
"The system rejects a payment attempt when the invoice status is not Open."
✓ The UAT translation
1. Navigate to Payments. 2. Find an already-Paid invoice. 3. Attempt to record a new payment. 4. Submit.
Expected: an error is shown, no payment recorded, status unchanged.

Three things make this work, and all three generalize to any AC you translate yourself:

Numbered, single-action steps

Each line is one physical action — "Navigate to X," "Submit." Nothing requires the reader to understand why the system behaves this way, only what to click.

A concrete, reproducible condition

The AC says "when status is not Open" — a category. The steps pick one concrete instance (an already-Paid invoice) rather than leaving the tester to invent their own, which might exercise a different code path entirely.

An observable expected result

"An error is shown, status unchanged" — every clause is something the tester can literally see. Nothing about a 409 or an exception class, which would be correct but invisible to this audience.

The same principle generalizes to cases that don't map onto "click a button, see a message": a scheduled-job AC is written as what the user observes the next business day, not how the job runs; an email AC is written as what the recipient receives, not how the email is sent — describe the world as the tester can observe it, never the mechanism that produced it.

Could someone who has never seen the codebase execute every step and judge Pass/Fail purely from what's in front of them?The check before you consider a translation done
What it actually costs

A Critical or High UAT finding doesn't mean a quick patch — it re-runs the entire pipeline for that story: fix, re-verify (the whole AC set, not just the failing one, since a fix can regress a passing AC), re-raise the PR, the suite-wide QA checks again, and UAT often resumes from scratch since a mid-checklist fix can change behavior already marked Pass. A single Critical finding on day one of a "half-day UAT slot" can consume the rest of the sprint's remaining calendar time. Budget UAT with slack at the end of a sprint, not flush against a hard release date — and take Stage 9's exit criteria seriously before UAT starts, since every defect caught there is a full fail-and-return cycle you never have to pay for.

Reference

What QA confirmation actually requires

The full suite passing, zero open Critical or High defects, and the coverage threshold met — that's the whole bar.

The coverage threshold is this project's own number, from standards/test-strategy.md — SDLC.md's "≥80%" is a default suggestion, not a framework-wide constant. Know which number applies to this project before you sign off.

Terminology recap
  • DeferredAllowed to cross UAT sign-off without being fixed, under the four-condition process. Never available to Critical.
  • QA confirmation vs. UAT sign-offTwo separate confirmations — the first technical (Stage 9's exit criteria), the second the PO operating the running system (Stage 10).
  • Coverage thresholdA per-project number from test-strategy.md, not a framework-wide constant.
Common mistakes ▸
  • Treating a High defect's deferral as approved because the PO signed the overall sprint sign-off.
  • Deferring a High defect where no real workaround exists.
  • Producing the full test execution report for a project with no external stakeholder who'll ever read it.
  • Skipping any form of QA confirmation because "the one-line note felt like overkill too" — the lighter artifact is still gated on the same exit criteria.
  • Writing a UAT step around an internal mechanism instead of what the tester can observe.
  • Letting a tester invent their own test data for an AC's condition.
  • Budgeting UAT as a flush-to-deadline half-day.
  • Assuming the coverage threshold is a fixed 80% for every project.
