Stage 9–10

Testing, QA & UAT

Two separate gates, not one step with two names. QA asks a technical question: does the code do what the stories said? UAT asks a business question: does the running system, operated by the PO's own hands, actually deliver what the BRD promised? A sprint can pass one and fail the other.

Defect severity

SeverityMeaningBlocks release?
CriticalUnusable, data at risk, or a security control bypassedAlways — no exceptions
HighCore feature broken, no viable workaroundUnless formally deferred
MediumDegraded, workaround existsNo
LowCosmeticNo

Two automatic escalations easy to under-apply: a defect found in production escalates one level; any security or cross-tenant data defect is always Critical, no proportionality exception.

The Deferred Defect Process
Critical defects can never be deferred, under any condition. A High defect needs explicit Product Owner agreement recorded against that one specific defect — not covered by a blanket sprint sign-off.Read condition 3 literally
✓ Correctly deferred — DEF-14, High
CSV export fails, but the on-screen data is fully usable, the Finance Manager confirmed export isn't needed until month-end (3 weeks out), and the PO recorded the decision against this specific defect with a target sprint.

All four conditions met, individually, for this one defect.

✗ Should not be deferred — DEF-15, High
Void Invoice silently fails for >10 line items — no error shown, no way for the user to know it didn't work.

No real workaround exists (the user can't even detect the failure). A silent, undetectable failure on a money-moving action should fail the PO's honest risk-weighing.

Process decision

When the full test execution report is warranted

Is there an external stakeholder who expects to be shown quality evidence? Is there a compliance or contractual reason a formal record has to exist? If no to both, a one-line sprint-plan note is sufficient.The trigger test

Skipping the full report doesn't mean a lighter bar — the suite still has to pass, Critical/High still has to be zero (or deferred), coverage still has to clear the threshold.

Density guidance

Turning an AC into something a client can run

Written for engineers
"The system rejects a payment attempt when the invoice status is not Open."
✓ The UAT translation
1. Navigate to Payments. 2. Find an already-Paid invoice. 3. Attempt to record a new payment. 4. Submit.
Expected: an error is shown, no payment recorded, status unchanged.

Numbered single-action steps, a concrete reproducible instance (not an abstract category), and an observable expected result — nothing about a 409 or an exception class.

Could someone who has never seen the codebase execute every step and judge Pass/Fail purely from what's in front of them?The check before you consider a translation done
What it actually costs

A Critical or High UAT finding doesn't mean a quick patch — it re-runs the entire pipeline for that story: fix, re-verify (the whole AC set, not just the failing one, since a fix can regress a passing AC), re-raise the PR, the suite-wide QA checks again, and UAT often resumes from scratch since a mid-checklist fix can change behavior already marked Pass. Budget UAT with slack at the end of a sprint, not flush against a hard release date.

Reference

What QA confirmation actually requires

Full suite passing, zero open Critical/High, coverage threshold met.

The coverage threshold is this project's own number, from standards/test-strategy.md — SDLC.md's "≥80%" is a default suggestion, not a framework-wide constant. Know which number applies to this project before you sign off.

Terminology recap
  • DeferredAllowed to cross UAT sign-off without being fixed, under the four-condition process. Never available to Critical.
  • QA confirmation vs. UAT sign-offTwo separate confirmations — the first technical, the second the PO operating the running system.
Common mistakes ▸
  • Treating a High defect's deferral as approved because the PO signed the overall sprint sign-off.
  • Deferring a High defect where no real workaround exists.
  • Producing the full test execution report for a project with no external stakeholder who'll ever read it.
  • Writing a UAT step around an internal mechanism instead of what the tester can observe.
  • Letting a tester invent their own test data for an AC's condition.
  • Budgeting UAT as a flush-to-deadline half-day.
  • Assuming the coverage threshold is a fixed 80% for every project.
