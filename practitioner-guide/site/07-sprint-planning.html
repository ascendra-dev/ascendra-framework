Sprint Planning

Stories are where the BRD's scope finally becomes something a developer can pick up without a follow-up question. Most of the risk in this phase is doing one command's job at the wrong point in the sequence, or trusting a number the framework hands you without a way to check it.

Decision heuristic

Choosing an estimation model

Time-Based is disqualified in the normal case. Its own reference file says AI implementation speed doesn't map linearly to human hours — every project here has an AI implementer. The one exception: a contract that requires hour-denominated billing regardless of accuracy — treat hours as a complexity proxy, not a time prediction.

Does this specific engagement already have a real Scrum velocity baseline? If yes, Fibonacci is viable. If no — the default state of every new project — choose T-Shirt.T-Shirt vs. Fibonacci, the real test
Using the real mechanism

The wave-vs-epic boundary

A wave is normally one epic — one /gen-stories run. It's legitimately more only when the pair carries a documented interleaving note.

Confirm the note names one specific story in the depended-on epic, not the whole epic. If it reads like a generic "these are related" gesture, push back before committing to paired generation.What to check at Step 8, before following either instruction
Sprint Assignment — well-designed, with one real gap

The split-boundary heuristic

Capacity is sourced from estimation.md, not invented. Three branches — at/near target, below target, above target — each with a deterministic action. The one gap: "above target" gives you the decision but not the tool.

The split should fall where the epic's own intra-epic dependency order already shows a natural seam — everything before it one coherent, demoable action, everything after it a distinct next action — not at whatever story happens to be eighth or tenth in the table.The seam heuristic, scaled up from the estimation standard's own Split Triggers
✗ Wrong split
Sprint the first ten rows of the planning table, carry the remaining three.

That cutoff has no relationship to what's actually buildable and demoable — it's just where the table ran out of room.

✓ Right split
Everything needed to create and persist a valid draft invoice → Sprint N. Everything that acts on an already-existing invoice → Sprint N+1.

Each half is one coherent, independently demoable scene — a Finance Manager either creates an invoice, or acts on one that already exists.

The check that actually enforces FW-048

A REQ can be correctly tagged, land in the right epic, and still produce a story that quietly depends on an untagged story. /review-stories check #7: for every Walking Skeleton: Yes story, every dependency — intra-epic or cross-epic — must itself be tagged. Not "practically fine" — a single non-tagged dependency is a finding, full stop.

Proactive, not just reactive

Story sizing before any file is generated

Does the bullet describe a brand-new pattern for this codebase? Does it plausibly touch more than half a dozen files? Does it read as two or three things joined by "and"?Apply at the Step 4 planning table, not after review flags it

Catching this at the table costs a slightly longer planning conversation. Catching it at /review-stories costs a Tier 3 fix on a story that already has ACs, an Out of Scope section, and dependencies written against the wrong boundary.

Full working depth

Wave vs. Sprint vs. Epic

Epic — fixed scope, decided once at approval. Wave — a unit of story generation, decided at /gen-stories time. Sprint — a unit of delivery cadence, decided later, purely from real story count vs. capacity. A wave and a sprint are not the same size and are not decided at the same time.

Worked, two personas, one capability

The tie-break rule

If two personas need the same capability, check whether the permission model actually distinguishes them — if not, pick the lower-privilege role.story.template.md §1

A "view an approved invoice's detail" screen (no Payer contact info) — both Finance Manager and Director genuinely need it, and the permission model doesn't distinguish them on this specific, narrowed scope. Written from the Director's side (the narrower role) forces the ACs to be built against the more restrictive permission set from the start, so a broader role is never the one implicitly excluded.

Common mistakes ▸
  • Selecting Time-Based because it "sounds more rigorous."
  • Choosing Fibonacci on a brand-new engagement with no velocity history.
  • Treating "generate the paired epic first" as self-justifying without confirming the interleaving note names a specific story pair.
  • Assuming one epic = one sprint.
  • Waiting for review to flag an oversized story instead of scanning the planning table first.
  • Splitting an over-capacity wave at whatever story lands eighth, instead of finding the real seam.
  • Writing a shared-capability story for the higher-privilege persona by default.
  • Accepting a Walking Skeleton story's untagged dependency as "practically fine."
