Stage 7

Sprint Planning

Stories are where the BRD's scope finally becomes something a developer can pick up without a follow-up question — the first Solution Domain artifact, gated on Locked architecture because a story's acceptance criteria have to be testable against something real. Three commands, three different jobs: /gen-stories proposes, /review-stories audits and sprint-assigns, /gen-sprint-plan turns the assignment into a kickoff document. As with epics, most of the risk here is doing one command's job at the wrong point in the sequence, or trusting a number the framework hands you without a way to check it. If that sounds abstract right now, keep reading — this chapter starts from zero.

What a story is, and why this is the first Solution Domain stage

What is a story? It's the smallest independently buildable, testable, and demoable unit of work — small enough that one developer can pick it up, build it, and verify it against its own acceptance criteria without needing several other things to land first.

Why can't this stage start any earlier? /gen-stories requires Locked architecture. Everything before this point — brief, domain knowledge, BRD, epics, screen design — deliberately had zero architecture dependency. Stories are the first artifact that needs to know the real tech stack, the real API shape, the real data model, because a story's acceptance criteria have to be testable against something real, not a placeholder.

Where does a story's content come from? Entirely from its parent epic — /gen-stories reads only the epic's In Scope bullets and Notes section, the same two fields Product Structuring covered. Nothing about how a story gets broken down or sized comes from anywhere else.

Decision heuristic

Choosing an estimation model

/gen-stories presents three options — T-Shirt Sizing, Fibonacci Story Points, Time-Based — as a menu with a one-line description each, and asks you to type a, b, or c. Read as a menu, all three look equally legitimate. Read the reference files themselves, and one of them almost always isn't.

Time-Based is disqualified in the normal case

Its own reference file states this about itself: "not suited for projects where the implementer is an AI assistant — AI implementation speed does not map linearly to human hours, making hour-based capacity planning unreliable." Every project run through this framework has an AI implementer, so this isn't a caveat that applies to some projects — it disqualifies the model for the normal case before you even get to comparing it against the other two.

The one legitimate exception: a client contract that requires hour-denominated billing or reporting regardless of accuracy — the same reference file names this directly ("client billing by hour, government contracts... clients who require hour estimates per story for approval"). If that's your situation, choose it, but hold the number the way the file itself instructs: treat hours as a complexity proxy, not a literal time prediction. You're not measuring how long the AI will take — you're producing a number the client's process requires.

T-Shirt vs. Fibonacci: the real test

Does this specific engagement already have a real Scrum velocity baseline — from a prior phase with this same client and team, or a client mandate that requires point-based reporting? If yes, Fibonacci is viable. If no — the default state of every new project — choose T-Shirt.The test

Both reference files state their own fit conditions plainly. T-Shirt is "best suited for AI-assisted delivery where implementation scope drives sizing more than human effort hours" — its capacity model is PO review throughput (PRs and change-request cycles per sprint), the constraint that genuinely governs an AI-implemented, single-PO-reviewed project. Fibonacci is explicitly "not suited for first sprints with no velocity history" by its own admission — capacity planning degrades to guesswork exactly when every new engagement starts. That's why T-Shirt is the framework's actual recommended default, not a cosmetic preference: Fibonacci measures a quantity this framework's delivery shape doesn't produce until several sprints in.

One more thing worth being honest about: even when Fibonacci is the right call because a real baseline exists, that baseline was almost certainly built on a different team/tool/domain combination than this specific AI-assisted engagement. Expect the first sprint or two to be noisy even with "real" velocity history — a baseline transfers imperfectly across a change in implementer.

Using the real mechanism

The wave-vs-epic boundary

A wave is the unit /gen-stories generates against in one run — normally one epic. It reads exactly one epic file, plans stories against exactly that epic's In Scope bullets, and reports on exactly that epic's story set. One command run, one wave, one epic — that's the default and it holds almost all the time.

It's legitimately more than one epic only when the pair carries a documented story-level interleaving note (Chapter 4). Once you've generated stories for an epic, the report tells you what to do next based on exactly that: if the epic carries an interleaving note with another epic, it says "generate stories for its paired epic now — their cross-epic dependencies mean they must be reviewed together." If it doesn't, it says review now. Until recently a PO had nothing to check that branch against except trusting the AI read the note correctly. Now you do.

Confirm the note names one specific story in the depended-on epic, not the whole epic. If it reads like a generic "these are related" gesture, push back before committing to paired generation.What to check at Step 8, before following either instruction

Open epics/index.md Section 3 yourself and read the interleaving note for the pair. If it names one specific story that has to land before another specific story, "generate the paired epic first" is doing its job — reviewing the pair together lets the epic-level Dependency Chain Coherence check verify that link once both files exist. If the note is vague, that's the same failure mode Chapter 4 taught you to catch at the source: don't let a soft note push you into generating and reviewing two epics together when the real dependency resolves cleanly at the epic level and one wave, reviewed alone, would have been correct.

Sprint Assignment — well-designed, with one real gap

The split-boundary heuristic

/review-stories Part F is the single best-designed mechanism in this phase. Capacity is sourced from estimation.md, not invented — the same file you set at the start. Three branches — at/near target, below target, above target — each have one deterministic action, not a vague "use judgment" instruction. Leftover stories are handled honestly: the "below target" branch surfaces the choice explicitly rather than silently rounding up or leaving a wave stranded.

The one gap: "above target" gives you the decision but not the tool. When an epic alone exceeds capacity, Part F's exact prompt asks where the split should fall — a real question with no worked answer anywhere in the command file. The naive answer, "put the first 8–10 rows in the table into the sprint, carry the rest," is exactly the arbitrary cutoff the estimation references themselves warn against.

The split should fall where the epic's own intra-epic dependency order already shows a natural seam — everything before it one coherent, demoable action, everything after it a distinct next action — not at whatever story happens to be eighth or tenth in the table.The seam heuristic, scaled up from the estimation standard's own Split Triggers
✗ Wrong split
Sprint the first ten rows of the planning table, carry the remaining three.

That cutoff has no relationship to what's actually buildable and demoable — it's just where the table ran out of room.

✓ Right split
Everything needed to create and persist a valid draft invoice → Sprint N. Everything that acts on an already-existing invoice → Sprint N+1.

Each half is one coherent, independently demoable scene — a Finance Manager either creates an invoice, or acts on one that already exists.

The check that actually enforces FW-048

Walking Skeleton Independence

Every phase before this one has already done something with the Walking Skeleton: the BRD tagged the requirements that compose it (Chapter 3), epics carried the tag forward and got sequenced first (Chapter 4). None of that guarantees anything real on its own. A REQ can be correctly tagged, land in the right epic, and still produce a story that quietly depends on a story nobody tagged — and the moment that happens, the "thin, real, end-to-end path" stops being either thin or independently provable.

/review-stories' epic-level check #7 (Walking Skeleton Independence — distinct from per-story check #7, Out of Scope Integrity, a different numbering track entirely) is where this actually gets caught: for every Walking Skeleton: Yes story, every dependency — intra-epic or cross-epic — must itself be tagged. Not "practically fine" — a single non-tagged dependency is a finding, full stop, because it means the path you're about to build first secretly isn't buildable first.

Where you'll actually see this bite: a Walking Skeleton story that needs some supporting capability — an audit log entry, a notification, a lookup table — where the natural story to depend on wasn't itself part of the tagged chain. The fix is never to quietly accept the dependency; it's to ask whether that supporting capability genuinely belongs in the skeleton (tag it too, using Chapter 3's own test — does the journey still run end-to-end without it) or whether the Walking Skeleton story's own scope was drawn too wide.

Part F also carries a lighter, upstream half of this discipline: Walking Skeleton ordering into sprints isn't a separate decision Part F makes — it's inherited automatically from the epic build order, as long as epics are worked through in that order. The one thing worth watching for yourself: a request to jump ahead and review a later epic out of sequence can quietly displace Walking Skeleton stories from the sprint that's supposed to prove them first.

Proactive, not just reactive

Story sizing before any file is generated

The story template's sizing rules aren't the gap — the AC-count proxy (3–10 ACs, XL must split) is checked consistently at generation, at review, and again at the sprint gate. The gap is that every one of those checks sits after the story breakdown is already fixed and files already exist. A story that's obviously going to come out L or XL gets caught once it's a real file with real ACs written against a scope boundary nobody questioned at the point where questioning it was cheapest.

Does the bullet describe a brand-new pattern for this codebase? Does it plausibly touch more than half a dozen files? Does it read as two or three things joined by "and"?Apply at the Step 4 planning table, not after review flags it

You don't have ACs yet at the planning table to run the formal proxy, but you don't need them to catch the obvious cases — the same over-fat tell Chapter 3 taught you to catch in a REQ, one level down. If more than two stories in the planning table already look L or XL on this rough read, propose splitting them right there. Catching this at the table costs a slightly longer planning conversation. Catching it at /review-stories costs a Tier 3 fix on a story that already has ACs, an Out of Scope section, and dependencies written against the wrong boundary.

Full working depth

Wave vs. Sprint vs. Epic

Epic — fixed scope, decided once at approval. Wave — a unit of story generation, decided at /gen-stories time. Sprint — a unit of delivery cadence, decided later, purely from real story count vs. capacity. A wave and a sprint are not the same size and are not decided at the same time — nothing forces the two numbers to align, and in a real project they usually won't.

Neither is a special case — it's Part F's three branches doing exactly what they're designed to do. The only discipline required of you is not assuming, walking into /review-stories, that "this epic" and "this sprint" mean the same thing — they don't, until Part F actually says so.

Worked, two personas, one capability

The tie-break rule

If two personas need the same capability, check whether the permission model actually distinguishes them — if not, pick the lower-privilege role.story.template.md §1

None of Harborview's three worked story examples ever exercises this rule — each has exactly one persona with no ambiguity about who else might want the same thing. Here's a hypothetical grounded in Harborview's real roles, clearly labeled as invented for this purpose.

Harborview's BRD defines Finance Manager (create, edit, void invoices; full data visibility including Payer contact details) and Director (approve or reject; view-only; Payer contact details explicitly not visible). Hypothetical story: "view an approved invoice's detail" — reference number, line items, totals, approval decision, approver name, with no Payer contact information anywhere on the screen. Both roles genuinely need it: a Director to confirm what they approved, a Finance Manager to confirm approval status before sending.

1. Do both personas need the same capability?

Yes — the same screen, the same fields, for both roles.

2. Does the permission model distinguish them here?

Check the data-visibility lines, don't assume. Director's restriction only bites if Payer contact details are shown — and this screen's scope deliberately excludes them. Scoped that way, nothing differentiates who can see it. The permission model does not distinguish them on this specific capability.

3. Pick the lower-privilege role

Director is the narrower role overall — view and approve/reject only, no create, edit, void, or Payer-management authority. Write the story from the Director's side.

Why this is the correct call, not an arbitrary one: writing the story for the broader role risks a developer implicitly gating the screen to that persona alone, since that's who's named in the ACs — silently locking the narrower role out of a capability they equally need. Writing it for the narrower role forces the acceptance criteria to be built against the more restrictive permission set from the start; the broader role, whose permissions are a superset for everything this screen touches, is never the one who ends up implicitly excluded.

If a later story needs to add something the narrower role genuinely can't see, that's a signal the capability has actually diverged and deserves a second story — not a reason to abandon the shared one.

  • Story-level interleaving noteDefined in Chapter 4; this chapter shows what to check with it at /gen-stories Step 8, not what it is.

Common mistakes ▸
  • Selecting Time-Based because it "sounds more rigorous."
  • Choosing Fibonacci on a brand-new engagement with no velocity history.
  • Treating "generate the paired epic first" as self-justifying without confirming the interleaving note names a specific story pair.
  • Assuming one epic = one sprint.
  • Waiting for review to flag an oversized story instead of scanning the planning table first.
  • Splitting an over-capacity wave at whatever story lands eighth, instead of finding the real seam.
  • Writing a shared-capability story for the higher-privilege persona by default.
  • Accepting a Walking Skeleton story's untagged dependency as "practically fine."
Harborview in practice

story.example.md's three worked stories are the model for density and structure in this phase, each a different shape.

US-01-005 — Generate invoice reference number

Backend logic, Size S. Its Notes section carries a real non-obvious constraint (single global database sequence, transaction-wrapped, gaps acceptable but year-boundary resets are not) that has no business being in an acceptance criterion.

US-01-002 — Create invoice form

UI, Size M. Its Out of Scope section correctly names the covering story for every excluded capability rather than gesturing at "handled later."

US-01-012 — Stripe webhook payment confirmation

Integration, Size M. Its ACs cover all four required categories in one story: happy path, boundary/rejection (partial payment), enforcement/idempotency (duplicate event), and audit (the audit log entry) — worth reading end to end as the reference instance of AC category coverage.

All three are Walking Skeleton: Yes — they satisfy REQ-008, REQ-006, and REQ-014/REQ-015, exactly the requirements tagged as part of Harborview's Walking Skeleton journey. US-01-012 depends on US-01-001 (invoice schema) and US-01-008 (invoice sending) — both load-bearing pieces of that same chain, nothing borrowed from outside it, which is exactly what a passing instance of Walking Skeleton Independence looks like.

sprint-plan.example.md

Worth reading for its Story Board and Delivery Sequence — six stories sequenced by technical dependency (schema before form, reference-number generation before the detail page that displays it) rather than by index order — and for a Sprint Notes entry showing the kind of pre-sprint operational note (seed data needed before a story is reviewable) that belongs there, not invented as an acceptance criterion.
