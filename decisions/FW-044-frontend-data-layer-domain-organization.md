## Decision

`gen-architecture.md`'s Step 5 Tech Stack table gains a **State Management / Data Fetching** row,
confirmed explicitly like every other row — but unlike Logging/Error Tracking (`FW-041`), its
confirmed value may legitimately be "None" (e.g. a project built entirely on Server Components).
The Tier 2 generation rubric now requires any confirmed frontend framework's standard to specify a
domain-namespaced organization for API-calling code, mirroring the backend's existing
module/controller/service requirement: a shared `lib/api/client.ts` (interceptors, cross-cutting,
one file) plus one `lib/api/{domain}.api.ts` + `lib/api/{domain}.types.ts` per domain, and — **only
if** the confirmed state-management/data-fetching approach uses hooks — one `hooks/{domain}.hook.ts`
per domain (never one file per hook, never a subfolder per domain). `/implement-story`'s Next.js
scaffold and Web implementation rules are updated to match: the shared client is generated once at
scaffold time, per-domain files are created by whichever story first touches that domain.

---

## The Problem That Triggered This Decision

Reviewing `ascendra-pay-web`'s real `signup`/`staff` pages found `lib/api.ts` accumulating every
domain's API functions in one file (separated only by comment dividers — `// ── Onboarding ──`,
`// ── Staff ──`), and `hooks/` as a flat folder with one file per hook and no domain grouping —
while `components/staff/` in the same repo is already domain-grouped. Compared against the
backend's `src/modules/{permissions,onboarding}/` structure (one module per domain, each with its
own service/controller/repository), the frontend has no equivalent boundary at all.

Tracing the root cause: `gen-architecture.md` line 364's Tier 2 generation instruction requires the
backend to specify "module/controller/service structure" but only requires the frontend to specify
generic "file/folder structure" — an asymmetric rubric, the same failure shape as the gaps `FW-041`/
`FW-042`/`FW-043` already found and fixed elsewhere. Separately, checking whether `@tanstack/react-query`
(a real dependency, and named by implication in `nextjs-standards.md` Rule 2's "`useQuery`-style
hook") was ever a *confirmed* stack choice found it was not: `system-architecture.md`'s Tech Stack
table has no "State Management" or "Data Fetching" row at all. It ended up in the standards' prose
without ever being an explicit, deliberate decision — the same shape of gap `FW-041` fixed for
Logging/Error Tracking.

---

## Why Tech-Stack-Agnostic Matters Here

Unlike Logging/Error Tracking, a client-side data-fetching/state-management library is not
universally required — a project built entirely on Server Components + Server Actions may
legitimately need none. The fix must not repeat the mistake it's correcting: assuming a specific
library (React Query) is always selected. Concretely, this means two things stay conditional,
never asserted as always-true:

1. **The Tech Stack row's confirmed value can be "None."** `gen-architecture.md` states this
   explicitly, so a future run never treats it as mandatory-to-select the way Logging is.
2. **The `hooks/{domain}.hook.ts` convention only applies if the confirmed approach uses hooks at
   all.** If Step 5 confirms no client-side data-fetching library, the hooks convention is omitted
   entirely from that project's Tier 2 standard — never generated by default, never assumed.

The `lib/api/{domain}.api.ts`/`.types.ts` convention, by contrast, applies regardless of the
state-management choice — API-calling functions and their types exist under any frontend approach,
hook-based or not.

---

## Scope of Application

Applies to `/gen-architecture` (Step 5's Tech Stack table, the Tier 2 rubric) and `/implement-story`
(the Next.js scaffold's client-generation step, the "API calls"/"Hooks" Web implementation rules,
and the Standards Compliance Self-Check). Does **not** apply to `ascendra-pay-web` — its existing
flat `lib/api.ts`/`lib/api-error.ts`/`hooks/*.ts` are untouched by this decision. Does **not** apply
to `ASCENDRA-PAY-001`'s own `system-architecture.md`/`nextjs-standards.md` either — retrofitting
those to record React Query as a confirmed choice and restructure the real files is a separate,
later Part 2, tracked outside this ADR.

## Relationship to Other Decisions

Refines the file organization `FW-042` (API contract) and `FW-043` (auth session module) already
generate into — neither of those decisions addressed *where* the generated code lives as a project
accumulates more domains, only *what* it must contain. Same root-cause shape as `FW-033`/`FW-034`/
`FW-041`/`FW-042`/`FW-043`: an asymmetric or missing rubric item, found by comparing the frontend's
real generated structure against the backend's.
