## Decision

Logging and exception handling are now a mandatory, never-skipped part of every project's confirmed stack and generated standards — a new `logging-standards.md` (Tier 1, cross-cutting) is always generated by `/gen-architecture`, the Tech Stack table always includes Logging and Error Tracking rows, every backend Tier 2 standard must specify a concrete global exception-filter/typed-business-exception pattern, every frontend Tier 2 standard must specify the framework's error-boundary convention, and `/implement-story` wires all of this into a repo's *first* scaffold rather than leaving it to whichever story happens to touch bootstrap code first. `ASCENDRA-PAY-001` itself — the project where this gap was found — is retrofitted in full: new `standards/logging-standards.md`; corrected `nestjs-standards.md`/`nextjs-standards.md`/`security-standards.md`/`api-standards.md`; a new `arch-v1.md` Section 6.5; real code in both `ascendra-pay-api` (`nestjs-pino`, `AllExceptionsFilter`, `BusinessRuleViolationException`, Sentry) and `ascendra-pay-web` (error boundaries, Sentry, a centralized `ApiError`/axios interceptor).

---

## The Problem That Triggered This Decision

A PO manual-review pass on `ASCENDRA-PAY-001` found that **neither `ascendra-pay-api` nor `ascendra-pay-web` had any logging or exception-handling infrastructure at all** — not a partial or buggy implementation, a complete absence:

- No logger of any kind in the API — no Pino, no Winston, not even Nest's own `Logger` used deliberately. Zero `console.*` calls either; errors simply had nowhere to go.
- No global exception filter, despite `nestjs-standards.md` Rule 1 stating `main.ts` sets one, and Rule 6 describing a `BusinessRuleViolationException` mapped to `422` in detail. Neither existed anywhere in the codebase. `ClassSerializerInterceptor` was in the same state — also claimed as wired, also absent — meaning `@Exclude()` on any sensitive field (Section 6.4) was not being enforced at all.
- No error boundary of any kind in the web app — no `error.tsx`, no `global-error.tsx`, no `not-found.tsx`.
- No error-tracking tool (Sentry or equivalent) on either side.
- `lib/api.ts` had a request interceptor (the bearer token) but no response interceptor — every caller handled a raw axios failure independently, with no shared shape.
- `security-standards.md` Rule 5 ("no sensitive value in logs") had been sitting in the standards file with literally nothing to enforce it, since no logger existed to configure a redaction policy on.

This is structurally identical to what `FW-034` fixed in `/gen-architecture` and what `FW-033` fixed in `/implement-story`: a standards file *described* a mechanism confidently enough that nobody thought to check whether it was actually built. The difference from those two: this wasn't one missed rubric item on an otherwise-covered topic — logging and exception handling had **no rubric presence at all**. `system-architecture.md`'s Tech Stack table had no Logging or Error Tracking row to prompt for one; `gen-architecture.md`'s Step 7 had no `logging-standards.md` in its Tier 1 list; nothing in Step 5 or Step 7 ever asked the question "how does this project log things, and what happens when something goes wrong?"

## Why This Was Missed for So Long

Every other cross-cutting concern in this framework's standards generation (auth, CORS, sensitive-field exclusion, audit columns) traces back to a concrete BRD-driven or security-driven prompt. Logging and exception handling have no equivalent trigger — no BRD requirement ever says "log things" the way one says "verify the user's session" — so a generation rubric built purely from BRD/security signals will structurally never surface it unless a rubric item exists independent of any specific requirement. That's the actual root cause, not an oversight in any single generation run.

## What Changed

**`gen-architecture.md`:**
- Step 5's tech-stack recommendation table gains Logging and Error Tracking rows, with an explicit instruction that these are *never* skipped or left "TBD" the way Payments legitimately can be (Payments has a real BRD-level open dependency; logging does not).
- Step 7's Tier 1 cross-cutting list gains `logging-standards.md`, generated the same way `api-standards.md`/`security-standards.md` are — never optional.
- `api-standards.md`'s generation instruction gains the `code` field on the standard error shape.
- `security-standards.md`'s sensitive-field-handling instruction now requires stating redaction as a structural mechanism, not an aspiration.
- Tier 2 (per-technology) generation instructions now explicitly require every backend standard to name its exception-filter/typed-exception pattern, and every frontend standard to name its error-boundary convention — closing the exact "came out right by luck" gap `FW-034` already named for JWKS verification.

**`implement-story.md`:**
- NestJS first-run scaffold gains a step wiring the logger, filter, exception class, and interceptor *before* the first story's endpoint is written.
- Next.js first-run scaffold gains a step wiring error boundaries, the API-error interceptor, and error-tracking instrumentation before the first screen is built.
- The Standards Compliance Self-Check gains a `logging-standards.md` re-check, alongside the existing `hard-instructions.md`/`form-validation-messages.md` checks.

**`projects/TEMPLATE/architecture/arch.template.md`:**
- Tech Stack table's illustrative rows gain Logging and Error Tracking.

- Part 2 Verification gains three checks: Section 6.5 present and concrete, Tech Stack has both rows, `logging-standards.md` exists and matches.

**`ASCENDRA-PAY-001` (the project itself):** see the `/assess-change` session record for the full blast radius — `standards/logging-standards.md` (new), corrected `nestjs-standards.md`/`nextjs-standards.md`/`security-standards.md`/`api-standards.md`, `arch-v1.md` Section 2/6.5/7.2/7.3, `arch-v1-ref.md` regenerated, plus real code in both repos (`chore/logging-and-exception-handling` branches, not yet merged as of this writing) and a retrofit of the two existing `400` business-rule rejections to `422`/`BusinessRuleViolationException`.

## Why Sentry and a Structured Logger Together, Not One or the Other

Structured logs (Pino → Axiom) answer "what happened, in order, across every request" — useful for debugging a specific reported incident once you know roughly when and where. Error tracking (Sentry) answers "what's currently broken, how often, for how many users" — useful for noticing a problem exists at all, with stack traces and breadcrumbs a raw log line doesn't give you. A solo-operator delivery model has no one else watching either signal proactively, so both are worth having from day one rather than choosing one and retrofitting the other once it's clearly needed — the entire premise of this decision is that "retrofit once needed" is exactly the failure mode that let this go unbuilt for an entire project's first two stories.
