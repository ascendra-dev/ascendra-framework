## Decision

A project may switch on **worklog mode** in its own `CLAUDE.md` when two or more people work on it at once. Each person then writes only their own worklog (`projects/{CODE}/worklogs/{name}.md`) and new files they create while those are Drafts. Every change to a main document (the decision log and its status section, the build index, approved plans, the design, the architecture note, the domain documents, the project rules) is written as a typed entry in the writer's worklog instead. The main documents change only in a `/sync-worklogs` session, run by the PO at each chunk's acceptance, or sooner for an entry marked Urgent. The sync checks every entry for textual and decision conflicts, puts every conflict to the PO at once, applies the rest, numbers the decisions, records the sync as a decision, and empties the applied entries. A project without the section works as before.

---

## The Problem That Triggered This Decision

ASCENDRA-PAY-004 moved to a PO and a developer working at once (2026-11-21). Every decision was a new numbered row in one table in `handoff.md`, statuses were hand-edited in `build/index.md` and the plans, and `/build-checkpoint` wrote Built blocks straight into a shared plan. Two people working in parallel would both add "decision 190", both edit the same status lines, and merge text git can join without noticing that the two decisions disagree. The PO proposed per-person files and one reconciliation session that resolves conflicts of meaning, not just of text.

---

## Key Design Decisions

- **Per person, not per artifact.** One worklog each means git never conflicts on documents: no two people write the same file. Considered first and set aside: one file per decision with date-and-initials IDs, and summaries generated by a script. It removes number clashes but not decision clashes, which still merge silently.
- **A closed list of entry kinds** (Decision, Built, Status, Change, Finding, New file, Question), each with a fixed body, and every entry naming its target section and the version it was written against ("Based on"). That lets the sync apply most entries mechanically and spend the session on real conflicts, and lets it detect a stale base.
- **Provisional IDs** (`Z-3`), never reset across syncs; the sync numbers them into the decision log in worklog order and records the map.
- **One author for the main documents.** Only the sync owner (the PO) applies a sync; anyone may run `check`. Main documents therefore always have one author and one consistent state after each sync.
- **Sync at chunk acceptance.** The PO is reviewing then anyway, and a chunk is the unit a pull request merges. Waiting longer lets conflicts grow; an entry that changes another person's current work is marked Urgent and calls an early sync.
- **The current state is the documents plus the unapplied entries.** A command that needs it (for example `/build-checkpoint`, reading earlier Built blocks in the same chunk) reads the worklogs as well as the plan.
- **The hold, for working directly** (PO's addition, 2026-11-21). Worklog mode shouldn't cost a sync when only one person is changing documents: a day working alone, or a planning session with Claude. Whoever holds the hold (`worklogs/hold.md`: who, since when, why) edits the main documents directly and writes no entries; the others keep writing their worklogs, so parallel work never stops. One holder at a time, taken by pushing that file and released by emptying it after pushing the edits; the sync itself takes it. Direct edits need no reconciling of their own: they are the documents, and the next sync's stale-base check compares every worklog entry against them. Considered and rejected: switching worklog mode off for the day, which would let both people edit directly if each thought they were alone.
- **A mode, not a new default.** One-person projects keep editing documents directly; nothing changes for them.
- **Code stays out.** Code goes through branches and pull requests in the code repos; worklogs hold only what documents should say about it.

## How Commands Use This

| Command | In worklog mode |
|---|---|
| `/sync-worklogs` (new) | Takes the hold, reads every worklog, checks, asks the PO, applies, empties applied entries, releases the hold; `check` writes nothing |
| `/build-checkpoint` | Writes its Built block and status as a Built entry in the builder's worklog, or into the plan for the hold's holder; reads earlier Built entries for the chunk from the worklogs |
| `/plan-build-group` | Writes the new plan file directly (a new Draft file); its build-index row and decision-log entry go to the worklog as New file and Decision entries, or directly for the hold's holder; re-planning an existing plan needs the hold |
| Any other change (a status, a correction, a finding) | Written as an entry by hand, or by Claude in an ordinary session, in the person's own worklog. `/update-status` and `/assess-change` belong to the full lifecycle and aren't used in projects built by design group, so they don't gain worklog mode |

A command finds the person by `git config user.name` in the project's `## Worklog mode` section.
